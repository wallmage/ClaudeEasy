# 安全更新热加载防断网设计

## 目标

- macOS 与 Windows 都保留热加载。
- 更新失败时自动恢复原配置，不重启、不退出 Clash。
- 同一次客户端运行期间，最多执行一次更新加载和一次恢复加载，禁止反复刷新把网络拖死。
- 用自动化测试阻止以后重新引入同类问题。

## 已确认的问题

macOS 旧流程绕过 ClashX Meta，直接让 Mihomo 重新读取配置。新版 ClashX Meta 同时管理内核、TUN、系统 DNS 和特权辅助进程；绕过客户端后，这几层可能不一致。连续加载与恢复会进一步放大故障，最终只有重启客户端才能重新同步。

## macOS 方案

1. 写入配置前记录当前客户端进程、运行配置、TUN 和代理组选择。
2. 写入后只向这个已经运行的 ClashX Meta 进程发送官方 `clash://update-config` 事件；不得通过 LaunchServices 启动应用，不得直接调用 Mihomo 的配置加载或 TUN 修改接口。
3. 按实际状态轮询，直到客户端进程未变化、配置已生效、TUN 与代理组保持原状态、DNS 和 HTTPS 连通性正常。
4. 若验证失败，恢复原文件，只再发送一次客户端原生加载并等待恢复完成。
5. 把客户端进程身份和加载阶段写进事务记录。同一客户端进程已经尝试过的阶段不得再次执行，后续调用只报告待恢复状态。

## Windows 方案

保留 Clash Verge Rev 的原生热加载快捷键，但加载后不再以“运行配置文件刚发生变化”作为完成条件。改为等待控制器、TUN、代理组、DNS 和 HTTPS 连通性全部稳定。更新加载与恢复加载各最多一次，并记录客户端进程身份，防止重复调用。

## 防止以后改坏

自动化测试必须拒绝以下改动：

- macOS 安全更新直接调用 `/configs?force=true` 或直接修改 TUN。
- macOS 通过 `open` 或 LaunchServices 启动 ClashX Meta。
- 任一平台在同一客户端进程中重复执行更新加载或恢复加载。
- 只检测文件变化、没有等待运行状态与实际网络恢复。

故障模拟覆盖：加载延迟、TUN/DNS 延迟、客户端退出或 PID 变化、更新加载失败、恢复加载失败、重复运行恢复命令。所有测试不得访问真实订阅，也不得操作正在运行的 Clash。
