## Diagnostics 模块

### 工作目标

用户沟通和连续执行遵守 [SKILL.md](../SKILL.md) 开头的最高原则。下列证据、假设和状态只供代理内部判断，用户主动询问前不展示。

**解决原始问题是 Diagnostics 的结束目标。** 分析或复核任务以原因、证据、反证和未知项完整为完成，不做未获授权的修改；修复任务中，只读检查才只是第一阶段，随后执行与证据对应的最小改动、复测和失败恢复。没有证据不能下结论，也不得直接执行 Patch 模块。

代理不请求用户确认诊断方案。已有授权、当前档位与产品边界内的本机检查、可恢复修复和复测连续完成；需要界面时按主入口的电脑操控规则处理。只有主入口列出的真实阻塞才提一个精确问题，提出前先完成其余准备；用户回复后直接继续。

### 任务合同、证据清单与授权边界

调用任何工具前，在内部建立四项**任务合同**：**任务对象**取用户完整描述中影响面最广的可观察问题；**交付类型**明确为分析、复核、修复、更新或监测；列出禁止动作和已有授权；**完成条件**逐项覆盖用户要求。应用、网站或错误提示可能只是发现问题的入口，是**下游症状**，不能越过更广影响面成为任务对象。每项检查、实验、写入或联网查询都要说明它推进哪项完成条件；不能推进就跳过。用户说故障已由其他流程处理、只要求解释时，不得擅自再次修复。

随后建立**原始证据清单**，依次定位用户时间线、先前自动化/代理/终端/任务运行器的原始执行记录、版本化备份和变更收据、应用与控制器日志、系统日志、配置差异和当前状态。来源名称不构成固定规则；摘要、转述和最后结论只用于定位原件。**已有历史证据**未读完前，不用当前健康状态或合成实验改写历史。每项新检查必须区分至少两个仍成立的解释，或补齐一个明确证据缺口；只证明“这种机制可能存在”的实验不能冒充事故现场。

维护一份**结论台账**，把症状、故障机制、故障来源、触发条件、恢复原因、修复动作和证据等级分开；新证据推翻旧判断时立即标记撤回，后续说明和动作不得继续引用旧判断。**工具调用失败只说明取证方法失败**，不能证明被查对象异常；连续两次工具调用失败时停止猜路径、参数或权限，先回读环境和工具能力，再选择另一条证据来源。

**使用 Skill 不等于授权修改 Skill。** 网络诊断、修复请求、产品反馈或发现保护缺口，都不授权修改仓库、提交或发布。只有用户**明确要求维护本项目**并把仓库置于范围时才进入产品改动；即使已有授权，也只能固化已经证实且可复用的问题，不能把事故候选写成产品规则。

持久修复必须以已经确认的问题为依据，并同时具备修改权限和明确对象。为取得证据而做的隔离实验，或用户已授权、单变量、可完整恢复的现场对照可以在确认前执行；**诊断对照不是持久修复**，只产生证据，不能写成问题已经解决。产品维护只固化已经由规则冲突、失败合同测试或可重复行为证实的通用问题，不把尚未证实的事故猜测写进代码、Skill 或项目规则。

### 交付类型决策表

| 交付类型 | 允许动作 | 完成条件 |
| --- | --- | --- |
| 分析或复核 | 只读 | 结论、证据、反证和未知项完整 |
| 修复 | 已确认的问题、明确对象和写入授权 | 最小修复、原场景复测和受影响能力回归 |
| 更新 | 用户明确要求更新全部订阅 | 不做更新前测试；备份并更新后，按已保存档位完成首次 Patch 的客户端动作、全部验收和最终复核 |
| 监测 | 只读采集；内容采集另需授权 | 确认采集运行、记录范围并提供停止方法 |

配置、用途档位变更和完整安全增强归入 Patch，完成条件按所选档位的验收规则执行。交付类型不能在执行中自行扩大；发现另一个值得处理的问题时，只记录并继续完成本次合同。

### 外部服务状态

只有任务合同已经把异常限制到单个外部服务时，才查询对应提供商的官方状态页和事件历史。影响跨应用、跨目标、跨网络层或跨订阅时，单个服务状态无法区分原因，不查询。记录查询时间、故障时间窗、事件状态、受影响组件与匹配程度；吻合只能算支持证据，没有官方事件也不能排除区域性或尚未公布的异常。

### 与用途档位联动

用途档位同时约束 Patch 和 Diagnostics。用途档位是 Diagnostics 的需求边界，不只是首次安装参数。每次诊断先读取已保存档位（macOS：`bash scripts/install_macos.sh --show-profile`；Windows：`.\scripts\install_windows.cmd -ShowUsageProfile`）；没有档位且后续需要修改时先完成用途选择，纯分析或复核保持只读，把档位如实记为未设置。把档位转换成三项约束：用户需要保持的能力、本次禁止触碰的设置、修复后必须复测的能力。故障本身不能自动升档；只有用户明确增加用途时才保存新档位，并按新档位重新确定范围。

- **档位 1：** 目标是国内域名稳定直连、普通境外网站可以通过系统代理稳定浏览。维护共同国内域名直连基线，但不检查或修改 TUN，不运行 DNS 泄漏、WebRTC 或 AI 检查，也不查看或修改 AI 分组、Claude 规则和第三档订阅增强。
- **档位 2：** 继承共同国内域名直连基线，目标增加 ChatGPT、Codex、Gemini、Perplexity 和 Agent 联网，并保持 TUN 开启、Clash 自己的系统代理关闭。可以在症状相关时检查 TUN 和 Agent 连接；档位 2 不运行 DNS 泄漏、WebRTC 或 AI 分组检查，也不安装或改写第三档订阅增强。
- **档位 3：** 诊断同时照顾普通浏览、海外 AI、Claude/Claude Code，以及档位 3 的既有能力。修复只涉及浏览器或单个应用时，复测原始症状和受影响能力；修改系统代理、过滤器、TUN、DNS、路由、Clash 或其他共同网络路径时，除原始症状外，必须只重测可能受本次改动影响的第三档能力，并在无法确认时保留“未验证”，不能为了修一个问题破坏泄漏防护或 AI 分流。只要任务实际执行了任何配置，不论配置是否最终需要写入，都必须在全部配置动作结束后按档位策略运行一轮本地区域指纹测试；每轮只测一次，中等风险或高风险完成一轮调整后再测下一次，直到低风险通过。纯只读分析不触发这项测试。

当前档位、本次范围、原始症状和档位回归结果记录在内部任务合同与完成清单中。没有执行某项高档位检查，是遵守用户选择，不是遗漏或失败。

### 通用工作循环

1. **执行任务合同。** 从用户原话中提取目标、动作、开始时间、频率和预期表现，锁定交付类型、禁止动作和完成条件。能从当前窗口、应用、截图、系统状态或日志自行确定的信息直接读取，只在缺少登录、实体操作或不可推断的用户选择时提一个简短问题。
2. **记录修改前基线。** 始终记录时间、操作系统、活动网络和原始症状，同时记录已保存档位。有 Computer Use 且症状能在有正常主窗口的应用中看到时，必须用用户实际使用的应用、账号、目标和动作在修改前复现；macOS 菜单栏应用改用脚本或结构化状态。`curl`、配置检查或另一个浏览器只能作为分层证据，不能替代原场景。无法复现时保持“尚未证实”，不得写“已修复”。只有当前档位允许，并且只有影响范围或证据指向共同网络路径时，才读取对应的 Clash 客户端与 Mihomo 状态。
3. **复现并缩小影响范围。** 优先复现用户的原操作。用范围矩阵判断是单个目标、一个应用、当前设备、当前网络还是共同路径：至少包含异常目标的单变量开关对照，以及至少两个健康对照在可疑组件开启时的表现。只有异常目标受影响时，先查目标与组件的交互；健康对照也出现同类故障时，才检查、修复或替换共同组件本身。一个应用异常而其他应用正常时先查应用层；多个应用同时异常时，再向系统、Clash 和网络层推进。相同服务不等于相同账号、接口或认证方式，对照成立前必须确认真正保持不变的条件。
4. **建立假设表。** 每个候选解释都记录支持证据、反证、下一项最便宜的验证和状态。状态只能写成 **已确认**、**有力支持**、**尚未证实** 或 **已排除**。单个现象或相关性只能算线索；除直接记录故障来源和机制的第一方现场证据外，关键判断至少需要第二种独立证据，并且必须主动寻找反证。
5. **按需取证。** 先读原始证据清单中的已有历史证据，再按现象选择必要层级，不是每次全部执行。每完成一项检查，都更新假设的状态和优先级；每项新检查必须区分仍成立的解释或补齐明确缺口。只有充分反证能排除某项解释时，才能标成“已排除”。
6. **检查解释是否完整。** 结论必须能解释全部已知现象，包括成功的对照、失败时间、范围和可量化差异。解释不了的观察必须保留，不能为了收尾而忽略。
7. **修复并迭代。** 一次只改变一个变量，保留修复前的状态和恢复方法。配置缺陷不等于故障原因；与原始症状无关但值得保留的增强必须单独说明，不能冒充修复。能在本机安全修复且属于用户要求的，由代理自动完成；需要管理员权限时由工具发起授权，不让用户抄命令。一次失败不是停止条件：安全拥有原状态且没有持久事务、外部替换或未知提交状态时，恢复后继续取证；否则保留现场和事务记录并按相应平台规则处理，不得强行覆盖。关闭应用、注销账号、删除或隔离缓存、Repair、重装或降级可能影响未保存工作、登录状态或本地数据，执行前必须说明精确对象、备份与恢复办法，并取得明确授权。Clash 客户端及其内核、辅助进程的启停、重装、系统 Repair，以及为修复它们而发起的重启或注销，只按 `SKILL.md` 共同安全边界处理，不得用本条授权。涉及节点、代理组、订阅或 TUN 时也遵守本项目边界。
8. **针对原始症状复测。** 使用同一原始动作、目标和应用比较修改前后结果，并检查健康对照没有变坏。间歇性问题要覆盖足够长的观察窗口；没有再次复现时写“暂未复现，观察中”，不能写“已修复”。

如果连续两次假设或修改没有改善原始症状，立即执行**诊断重置**：停止继续试改，恢复全部未生效的试验，重新列出已确认、已排除和未知项，并从原场景重新测量各层时间线。诊断重置后继续收集最有区分度的新证据；没有新的证据不得进行第三次修改。不得把前两次失败当成继续猜第三个设置的理由，也不得把诊断重置当成停止工作的理由。

### 因果判定门槛

先按结论范围选择门槛。单次事故只要求现场时间线、能定位机制或来源的直接证据、反证和恢复归因；不能因样本只有一次而强行要求总体统计。凡是准备把伴随事件、设置、进程、设备、节点或服务写成反复故障的“主要原因”，才必须额外完成以下记录，缺一项就不能升级为重复模式结论：

1. **事件真实性：** 从原始来源识别真实事件并人工抽查样本。日志里的原始事件与引用、摘要或诊断文本必须分开；解析器命中一个错误字符串不等于发生了一次错误。
2. **时间方向：** 候选原因必须先于症状，并落在事先定义的合理窗口内。症状之后发生的事件不能倒算为原因，也不能看完数据后不断扩大窗口去凑匹配。
3. **两个分母：** 在同一可比时间范围内统计全部候选事件和全部故障。候选事件命中率是“候选事件后发生故障 ÷ 全部候选事件”；故障覆盖率是“故障前存在候选事件 ÷ 全部故障”。不报告分母的次数没有因果解释力。
4. **正反例：** 同时列出“有候选事件但没有故障”和“没有候选事件却发生故障”。反例占多数，或候选解释不了大部分重复故障时，最多保留为偶发触发条件，不能称为主要原因。
5. **证据独立性：** 多个记录如果只是同一个下游现象的复制、转述或派生，就不能算两种独立证据。独立证据必须从另一条因果路径支持候选原因与症状之间的上游联系。
6. **单变量干预：** 在其他条件相同的情况下只加入、移除或替换候选原因，重复触发与恢复原始症状。无法安全执行单变量干预时，必须用一条直接记录上游失败的独立证据替代；否则状态只能是“有力支持”或“尚未证实”。

机制解释只能说明为什么可能发生，不能补足实测证据。投入时间、用户要求唯一答案、已经公开过某个判断或终于找到一个说得通的故事，都不能降低因果判定门槛；证据不足时继续取证或如实保留未知项。

结论必须使用以下固定结构：

| 状态 | 结论措辞 |
| --- | --- |
| 全部门槛通过 | `已确认的主要原因：X`，随后列最关键证据和复测结果 |
| 尚缺任一门槛 | `下一项验证：X（有力支持/尚未证实）；尚缺门槛：……` |
| 反证充分 | `已排除 X 作为反复故障的主要原因`，并保留尚未排除的有限作用 |

未确认候选不得称为“最可能的主因”“首要原因”或同义词，再附“尚未确认”也不合格。只有 X 已排除且 Y 已确认时才能写“不是 X 而是 Y”；不能用排除一个错误解释来证明另一个候选。

### Computer Use 与 Sub Agent

电脑操控的能力检测、启用、授权与平台分工以 [SKILL.md](../SKILL.md) 和当前平台文件为准。Diagnostics 只补充两点：每次界面操作后重新读取可见状态确认结果；能通过文件、脚本或结构化接口可靠完成的事情优先使用它们。Codex 的当前设置见 [OpenAI Computer Use 文档](https://learn.chatgpt.com/docs/computer-use)；ZCode by Z.ai 的电脑控制支持与权限提示见 [ZCode 官方更新说明](https://zcode.z.ai/cn/changelog)。

预计超过 10 分钟、步骤很多，并且至少有两路彼此独立的只读证据时，可以启用多个 Sub Agent。主代理先读取用途档位、定义问题范围和统一时间窗，再按应用界面、Mihomo 连接、系统网络或日志来源拆分任务。Sub Agent 只返回带时间戳的事实、反证和未知项，不运行安装、卸载、订阅更新、配置恢复或任何写入命令。整个任务同时只有一个界面操作者和只有一个主动流量生成者，避免抢鼠标或让并发测试污染计时和连接记录。所有写入、更新、恢复和最终判断都由主代理串行完成。短任务、同一界面操作、同一文件事务或互相依赖的步骤不得为了形式而拆分。

### 判断防线

| 容易误导用户的想法 | 必须执行的动作 |
| --- | --- |
| “命令行很快，页面应该已经好了” | 回到用户实际使用且有正常主窗口的应用，用 Computer Use 验证原始动作；macOS 菜单栏应用改用脚本或结构化状态。 |
| “这个配置确实不理想，所以就是它” | 把配置问题与当前故障分开；先做单变量对照和寻找反证。 |
| “关掉一个网站的过滤后变快，整个过滤器都坏了” | 完成范围矩阵；不能因为单个目标的对照结果就停用或删除整个组件。 |
| “又发现一个慢网站，再加一个例外” | 测试至少两个健康对照；同类故障跨目标出现时修共同组件本身。 |
| “前两次没用，再试一个设置” | 诊断重置；没有新的证据不得进行第三次修改。 |
| “这次打开挺快” | 对无副作用场景用同一应用、目标和动作连续测试三次。 |

如果现有记录覆盖不到异常时段，自动建立有开始时间、结束时间和采样间隔的观察窗口。必须记录采集工具或会话、进程或任务标识、采集范围、开始与结束时间、停止与清理方法，并确认采集正在运行。优先记录计数、时序和连接元数据；除非更轻量的证据不足且用户已授权，不抓取通信内容。问题再次出现后，按时间线关联证据并关闭观察，不让监测无限运行。工具无法持续运行时写“未建立监测”，不得承诺下一次会自动采集。

观察时长由原始故障决定。可以立即重复的问题，修复前后各连续测试三次。间歇性问题优先覆盖最近记录中的典型复发间隔；捕捉到一次异常后，修复后至少观察同样长的时间窗。没有历史可参考时先建立短窗口，仍未出现就按用户描述的频率延长，并保持“观察中”。

连续复测不得增加账号或业务风险。重复动作会提交登录、支付、发消息或其他有副作用的请求时，先检查失败次数、限流、验证码和锁定风险；出现迹象就停止重复提交，改用日志、只读接口或无副作用对照。Computer Use 可以读取界面并执行不含敏感输入的步骤；密码、验证码、MFA 或硬件确认由用户完成，代理不得记录或转述。

### 证据选择

以下是可选证据层，不是固定清单：

- **应用与浏览器：** 对于有正常主窗口的应用与浏览器，有 Computer Use 时必须用它重现操作，读取可见错误、加载状态和开发者工具中的失败资源；macOS 菜单栏应用改用脚本或结构化状态。把 DNS、主文档与关键资源的网络耗时、首次显示和加载结束分开记录；主文档很快但页面仍空白时，优先检查脚本、Service Worker 和扩展注入，不得继续归咎 DNS 或 Clash。比较同一目标在另一个浏览器、无扩展窗口或同应用新会话中的表现；怀疑扩展或过滤器时先完成异常目标与至少两个健康对照的范围矩阵。单站对照无改善立即恢复；只有跨目标证据成立时才修共同组件本身。
- **DNS：** 比较系统解析、Mihomo `/dns/query`、A/CNAME、缓存状态和相关 DoH 的结果。只有证据指向解析或 CDN 错位时才清缓存或改 DNS；`DIRECT` 规则本身不能证明解析路径正确。
- **分流与代理：** 从 Mihomo `/connections` 读取目标、进程、命中规则、`rulePayload`、连接链、出站和字节计数。代理内核持有连接只说明流量经过它，不能单独证明是内核发起了业务请求。
- **传输：** 按需要测 DNS、TCP、TLS、首字节和总耗时，以及丢包、抖动、重传、接口错误和可用带宽。网页慢、连接失败和实时音视频卡顿使用不同指标，不能拿一次测速替代原场景。
- **系统与进程：** 查看当前进程、Socket、网卡计数、路由表和实时收发变化，再定位产生连接的应用。先看元数据和时间范围，避免无边界扫描用户文件。
- **历史与日志：** 先锁定异常时间线，再读取相关系统记录和应用日志。通过进程、连接目标、文件更新时间和事件类型定位日志，不按一张预设应用名单搜索。大日志、进程存在或时间接近都只是线索，必须与独立证据交叉验证。
- **泄漏与安全：** 只对档位 3 运行相应网页与连接验证。档位 1、2 用户明确增加泄漏防护需求时，先改为档位 3，再检查和修复；不得因一次故障报告自行升档，也不得把完整补丁验收当成每次诊断的固定步骤。

### 重叠接管与职责分层

多个无关网站或应用都在内容开始传输前等待近似固定时长、随后快速完成时，先按当前档位建立网络接管清单。档位 1 只检查系统代理或 PAC、浏览器内容过滤和与原始症状直接相关的层，不查看 VPN 或 TUN；档位 2、3 在证据指向共同路径时才加入透明代理或内容过滤器、VPN 或 TUN、DNS 过滤器、防火墙和终端安全软件。设置同时开启只能证明存在重叠，不能证明发生冲突；至少取得以下两类证据：原场景的等待与握手超时、重置或假地址处理失败在时间上对应，以及保持其他条件不变时切换一个组件的兼容模式能稳定消除等待。

确认重叠接管后做职责分层：同一流量层只保留一个透明接管者；内容过滤只覆盖浏览器时，可以把它放到遵守系统代理的应用层，让 VPN 或 TUN 继续负责最终分流、DNS 和 UDP；需要覆盖全部应用或特殊协议时，选择厂商支持的其他组合或明确排除范围。具体模式由用户需要的覆盖范围和厂商限制决定，不能把某个产品的兼容开关写成通用答案。

修复验收同时包含三类结果：原始症状在至少三个不同目标上连续复测；广告过滤、证书处理或应用覆盖等原有功能覆盖仍符合用户需要；当前档位中可能受本次修改影响的能力和安全属性保持正常。只有档位 3 才把 DNS 泄漏、WebRTC 和 AI 分流列为安全回归项。删除诊断期间添加的临时站点规则，不逐站添加例外。任何必要项目不通过都恢复修改前的接管模式，并保留“尚未解决”。

### 第一档已知故障：国内请求误走海外

这是三个用途档位共同继承的共享故障，不是某个网站的专用问题。国内网站或国内应用出现间歇性打不开、同步失败、连接被重置或几分钟后自行恢复时，直接检查以下判据：

1. 目标域名存在于受管国内域名数据集；
2. Mihomo 实时连接却命中 `MATCH`、国外规则或海外代理，而不是受管国内规则与 `DIRECT`；
3. 大陆 DoH 与直连得到国内 CDN 且稳定，当前解析或代理出口得到境外 CDN、超时或重置；
4. 至少一个同类国内目标也受共同路径影响，或配置检查证明全部订阅都缺少共同基线。

满足前 3 项即可确认选路错误；第 4 项用于判断影响面，不能为了凑对照拖延修复。修复必须覆盖当前存储位置中的全部订阅，不能只改当前订阅，也不能给 Kimi、欧陆词典或其他单站添加例外。

共同基线由 `policy.json` 的 `cn_domain_provider` 唯一定义。同一提供器同时驱动 DNS 与连接路由，避免两者使用不同名单。档位 3 的受管 AI 规则独占相同匹配键；其他显式用户域名规则仍按原顺序保留。受管国内规则位于宽泛 `GEOSITE`、`GEOIP`、`RULE-SET` 与 `MATCH` 之前。若默认名称或缓存路径已被用户占用，用 `-2`、`-3` 递增并生成对应路径；缓存路径按 Mihomo HomeDir 所在文件系统的大小写与 Unicode 等价规则比较，绝不覆盖路径别名指向的用户缓存；只更新能以名称、URL 和受管路径共同确认所有权的条目。

macOS 每次安装或订阅更新都按当前档位逐份转换当前存储位置的顶层订阅；档位 1、2 只加共同基线，档位 3 再加完整增强。Windows 三档都安装带数字档位的全局脚本，让每份订阅加载或刷新时使用相同基线。规则提供器由 Mihomo 每天更新，不实现后台订阅监听。

Diagnostics 不需要重新发明排查顺序：逐份核对提供器、DNS 引用和路由引用，再核对活动配置、提供器更新时间、Fake-IP/DNS 缓存和实时 `DIRECT` 连接。当前无法重现应用症状时，只能写“暂未复现”；配置已修复与历史间歇性现象已证实消失必须分开报告。

### 多个订阅全红、共用运行状态与节点 Fake-IP 地址

多个独立订阅或无关目标同时失败时，先把证据分成共用运行状态与每份配置状态。控制器内核、DNS/Fake-IP 缓存、监听端口、系统 DNS 和接管层属于共用运行状态；订阅字段、节点域名与健康检查属于每份配置状态。多个订阅可能共用一个故障，也可能只是先后暴露两个独立故障，不能从“都红”直接推断同一原因。修改文件、加载配置、清空 DNS/Fake-IP 缓存、修改端口或连接同时发生属于组合操作，必须逐项写入时间线。组合操作后的恢复只证明这一组变化与恢复窗口重叠，不能证明其中任何一项单独有效。同一份配置未修改而恢复，只能排除需要持续存在的文件错误；共用运行状态恢复、自然过期和外部状态恢复必须分别验证。最后一次确认失败到首次确认恢复之间才是恢复窗口；首次复测延迟时，不得声称某项操作即时生效，也不得把窗口内的正常流量当成修复。没有单变量对照或直接上游记录时，不得把恢复归给改过的配置文件。订阅名称只用于当次事故标签，不进入诊断规则、自动修复条件或测试。

多个订阅显示全部节点不可用时，仍把它们当成多份待验证对象，不假设同一原因。在用户切换订阅前，保存当前订阅的节点健康检查、节点域名解析和有明确起止时间的控制器实时日志；文件日志目录不存在、不可读或不可写时记录证据缺口，改用控制器实时日志，不能等切换后拿另一份订阅的日志补齐。用户已经切换时仍逐份订阅取证；一份订阅的现场证据不得共用结论到另一份，原订阅证据已丢失时保留“尚未证实”。

#### 多订阅故障的证据顺序

以下顺序按证据依赖执行，不按时钟切割。能立即定性就立即给结论；证据不足时只执行最能区分当前候选的下一项检查，**不得为诊断阶段设置任意分钟数**，也不得为了显得迅速而跳过必要证据：

1. **固定时间线。** 记录最后正常、首次失败、每次订阅切换、测速、文件写入、配置加载、缓存清理、端口变化和首次确认恢复；保存当时的 Mihomo PID、当前配置哈希和配置切换缓存。按原始证据清单定位先前自动化、代理、终端或任务运行器的**原始会话或审计记录**，核对实际命令、返回值和时间，不能拿最终总结代替操作证据。
2. **先取最能区分原因的日志。** 当前订阅优先保存控制器实时日志、节点健康检查和节点域名解析；同时检查文件日志是否可写。文件日志失败不等于历史证据不存在：macOS 查询 `/usr/bin/log show --info --debug`；Windows 文件或应用日志缺失时，改查控制器记录，以及有明确时间和目标范围的 `pktmon` 或系统连接证据。macOS 内核 TCP 摘要的记录者是 `kernel`，因此 predicate 使用 `process == "kernel"`，再在 `eventMessage` 中匹配本轮实际 Mihomo PID；不能用 `process == "mihomo"` 查不到后就宣布没有日志。一种采集方法失败不能宣布没有历史证据。输出前按单条记录同时匹配进程、时间、接口、目标端口和传输计数。
3. **逐份按传输表现分类。** 同一 TCP 摘要在物理接口上出现 `SYN in/out: 0/1`、`RST in/out: 1/0` 和真实 RTT，表示本机已经发出连接并被外部端点或途中设备拒绝；它能定位到本机之外，但不能区分入口程序、防火墙、防护系统、机房或上游线路。节点连接日志出现“节点域名 → `198.18.0.0/15` → 超时”，并且直连 IP 加密解析器为同一域名返回真实地址，才支持该订阅的节点启动解析进入本机 DNS/Fake-IP 链。Fake-IP 模式下，经 Mihomo 查询普通域名得到 `198.18.*` 是 **Fake-IP 模式的正常应答**；`nslookup` 这种结果不能证明缓存污染。
4. **形成原因矩阵。** 每份订阅分别写“本机配置、共用本机状态、外部拒绝或证据不足”，列最能排除其他解释的证据和唯一缺口。**故障原因与恢复原因**分开判断；没有修复后立即用原订阅复测，或一次执行了组合操作，就不得声称某一项修好了它。已经单独确认且获授权的本机故障可以使用安全事务恢复服务，但不能替其他订阅下结论，也不能扩大产品修改权限。

ClashX Meta 统一日志出现 `DDFileLogManagerDefault` 的 Cocoa 257/513 或 POSIX 13，且 `~/.config/clash.meta/logs` 或当前会话子目录对当前用户不可搜索、不可写时，运行 `ruby scripts/macos/patch_profiles.rb --repair-clashx-logs --json`。操作必须先拒绝符号链接、不安全的配置根目录和 root 身份；必须保留旧日志，也不能 `chown`。旧目录只在不可覆盖改名期间临时恢复当前所有者所需的访问位，随后以原权限完整保留为 `logs.permission-backup-*`；新目录设为 `0700` 并加入当前用户可继承的读写与目录访问 ACL。能够识别原会话目录时在新目录中重建同名空目录，让仍在运行的客户端恢复写入。新树创建失败时删除仍为空且身份未变的本轮目录；旧树已经改名并发布新树后再失败则返回 `partial/log_repair_partial`，不能报告零修改。最后用一次无害代理请求确认新 `clashx_*.log` 出现并增长，同时确认统一日志不再出现权限错误；不能确认时返回 `log_runtime_unverified`，权限已修改则标记为 `partial` 且只报告 `log_directory_permissions`，继续使用控制器实时日志，不声称文件日志已经恢复。

节点连接日志同时出现节点域名、当前 Fake-IP 地址和连接超时，并且同一域名经直连 IP 加密解析器得到真实地址时，才确认该订阅的节点启动解析进入本机 DNS/Fake-IP 链。再核对系统 DNS 接管者、AdGuard 上游、Mihomo `dns-hijack` 和 `proxy-server-nameserver`，说明完整路径；普通域名经 Mihomo 查询得到 Fake-IP 是正常行为，不能当作补充证据。只有配置机制而没有该订阅的连接证据时仍是候选解释。

确认后调用已保存档位的 macOS 安装入口修复三个档位共有的节点启动解析基线，并逐份复测节点健康、DNS、当前运行端口和原有代理组选择。不得手工改订阅、不得直接强制加载、不得只清缓存冒充修复，也不得切换订阅、代理组或节点。Windows 遵守下述运行中写入边界。

### 已知证书故障：系统 PAC 所有权、短暂中断与 Fake-IP 重用

应用偶发服务器身份验证失败时，不套用国内分流修复。若统一日志显示 CFNetwork 路径 `uses proxy`、连接到本机 AdGuard 监听端口并出现 TLS 信任错误（如 `-9802` 或 `CERTIFICATE_VERIFY_FAILED`），而当前同一主机的证书链与主机名校验正常，随后同一路径重试成功，先按系统代理所有权冲突、PAC 查询中断或 Fake-IP 重用调查。单独看到 AdGuard、Fake-IP、某个订阅节点或 Clash `ProxyConfigHelper` 活动都不是结论；必须把 PAC 查询、端口所有者、代理配置变更、AdGuard 连接目标和 TLS 失败放进同一时间线。

先读取系统 PAC 地址并确认回环端口由哪个进程监听，再读取 Clash 客户端自己的系统代理状态。档位 2、3 的基础组合是“Clash TUN 开、Clash 系统代理关、AdGuard 自动代理开”。若故障窗口显示 Clash 的 `ProxyConfigHelper` 正在改动或争用系统代理，且 Clash 自己的系统代理确实开启，macOS 运行原生开关协调命令关闭 Clash 系统代理，Windows 按平台界面规则处理；保留 Clash TUN、AdGuard 自动代理和 HTTPS 过滤。

Mihomo 使用 Fake-IP 时，再从 AdGuard 日志读取故障连接的应用、目标域名和 `198.18.0.0/15` 目标地址，只输出时间、域名和假地址；同时从 Mihomo 持久 Fake-IP 数据库的只读快照读取该地址当前的反向映射。只有两项同时成立才确认 **Fake-IP 被重新分配**：AdGuard 在失败时把目标域名连接到某个 Fake-IP；同一个 Fake-IP 现在映射到另一个域名。错误域名与证书域名一致是第二项独立证据。不能只凭地址落在 Fake-IP 网段、当前证书已经恢复或刷新成功下结论。

确认后检查运行配置的 HTTP 或 mixed 代理端口，并用监听进程、控制器运行配置和一次代理请求三重确认该端口正在由当前 Mihomo 监听。不得固定假设为 `7890`。记录 AdGuard 出站代理的开关、协议、主机、端口、用户名、证书信任和 UDP 选项；已有的非 Clash 出站代理不覆盖。原状态为关闭时，只通过 AdGuard 界面设置 **AdGuard 出站代理**为 HTTP、`127.0.0.1` 和已验证的 **Mihomo HTTP 代理端口**，用户名和密码留空，证书信任与 UDP 选项保持关闭。这样 AdGuard 通过 HTTP `CONNECT` 按域名把过滤后的请求交给 Mihomo，不再把可能被重用的 Fake-IP 交给下一层。原状态已经是本工具要求且端口仍属于当前 Mihomo 时不重复修改。

修改后用原应用连续复测原目标三次，并复测至少三个无关目标；从 AdGuard 日志确认新连接不再以 `198.18.0.0/15` 假地址作为出站目标，从 Mihomo `/connections` 确认目标域名、规则和连接链正确。再确认 Safari 和 Chrome 的广告过滤、HTTPS 证书处理以及当前档位可能受影响的能力。任一项目失败就通过 AdGuard 界面恢复 AdGuard 原状态；恢复后回读全部记录字段。恢复失败时停止，不继续叠加修改。

禁止按应用调整 AdGuard 过滤范围；应用名单不可穷举，也不能作为产品级修复。Clash TUN 存在时不得把 AdGuard 改为 `Network Extension`。不得点击忽略证书的“继续”，不添加 Apple、iCloud 或单站规则，不得全局关闭 HTTPS 过滤，也不得把当时使用的订阅节点当成原因。不得直接编辑 AdGuard Plist、第三方 PAC 或系统代理。当前无法复现或没有 Fake-IP 重新分配证据时不改出站代理，写“暂未复现，观察中”，不能把当前证书正常写成历史故障已经消失。

### AdGuard for Mac 已知兼容路径

这是 macOS 上 Clash TUN 与 AdGuard for Mac 共存的产品规则，同时用于 Patch 和 Diagnostics。[AdGuard 官方兼容说明](https://adguard.com/kb/adguard-for-mac/solving-problems/big-sur-issues/)也把从 `Network Extension` 改为 `Automatic Proxy` 作为与部分 VPN 或透明代理冲突时的处理方式。该规则只适用于档位 2、3，因为这两档由 Clash TUN 负责最终分流；它不是升档，不增加当前档位之外的 DNS、WebRTC、AI 分组或订阅改动。Clash TUN 存在时不得把 AdGuard 改为 `Network Extension`，禁止按应用调整 AdGuard 过滤范围。档位 1 依赖 Clash 的系统代理，不能让 AdGuard 自动代理再占用同一个位置；Windows 的过滤机制也不同，两者都不能照搬。

Patch 在切换档位 2、3 的客户端开关时同时检查 AdGuard for Mac。检测到 AdGuard 正在使用 `Network Extension`，就记录当前模式和保护状态，通过 Computer Use 只通过 AdGuard 界面切换到“自动代理”，保持 Clash TUN 开启、Clash 自己的系统代理关闭。运行配置使用 Fake-IP、AdGuard 出站代理原本关闭且当前 Mihomo 的 HTTP 代理端口可以按上述三项证据确认时，再通过 AdGuard 界面配置本机出站代理，避免 AdGuard 把缓存的 Fake-IP 当作普通目标地址交给 Mihomo。已有的非 Clash 出站代理保持不动并报告未修改。不得用 `networksetup`、defaults、Plist 编辑或脚本改写 AdGuard 与系统 PAC，不得退出、停用、卸载或重启 AdGuard，也不得添加逐站例外。

Diagnostics 遇到多个无关网站都先空白或转圈约 10–30 秒、随后很快显示，并且现场存在 Clash TUN 与 AdGuard `Network Extension` 时，直接把这条已知兼容路径作为第一项单变量对照，不再从零试一串站点规则。仍要在切换前用原应用复现并记录等待时间；不能仅凭检测到 AdGuard 就宣布故障原因。切换后用同一应用和动作连续复测原目标及至少三个无关目标，并确认 Safari 和 Chrome 的广告过滤仍符合用户需要。档位 2 再复测普通 AI 与 Agent 联网；档位 3 只复测本次共同网络路径可能影响的分流、DNS 与 WebRTC 能力。

自动代理只覆盖遵守系统代理的程序，Safari 和 Chrome 等浏览器通常仍会被过滤；非浏览器应用可能不再经过 AdGuard，必须在修改前向用户说明。AdGuard 出站代理只改变过滤后流量交给 Mihomo 的方式，不扩大 AdGuard 的应用覆盖范围。任何原始等待无改善、广告过滤失效、档位能力变坏或覆盖范围不符合用户需要的情况，都要无改善立即恢复 AdGuard 原状态，并继续通用诊断。不能把这个 AdGuard 专用兼容路径写成其他过滤器或 VPN 的通用答案。

macOS 当前流量优先使用 `nettop` 的按进程/连接 CSV、活动监视器的网络计数、`netstat -ib`、系统 DNS/路由状态和 Mihomo 连接记录。macOS 不保证保存一份可直接按应用回放的长期流量历史；历史不足时建立观察窗口，并用相关应用日志补充，不能假装已取得过去的逐应用字节。

Windows 历史总量优先读取 `ConnectionProfile.GetNetworkUsageAsync` 返回的 `NetworkUsage`，按时间粒度汇总 `BytesSent` 与 `BytesReceived`，并覆盖异常期间使用过的全部网络配置；当前网卡使用 `Get-NetAdapterStatistics`。网页分阶段耗时优先使用系统自带的 `curl.exe`，TCP 端口对照使用 `Test-NetConnection`，连续时延和丢包使用 `Test-Connection`；实时应用优先读取应用自己的质量统计。需要捕捉复发问题时，可使用有明确时间和目标范围的 `pktmon` 计数或过滤采集。SRUM 或受保护的逐应用数据只有在确有必要、获得权限且能安全只读时才使用；聚合总量不能冒充逐应用归属。

日志与开发者工具只读取必要时间窗和必要字段。

### 判断与修复

禁止把“可能是”包装成结论。代理应优先设计能区分两个候选解释的检查，而不是继续罗列可能性。涉及数量时核对时间范围、单位、累计值与增量值，并检查推导是否能覆盖观察到的数量级；数学接近仍需独立证据确认对象和行为。

证据指向 Clash 配置时，先区分单项故障、三个档位共有的安全基线和档位 3 完整增强。先只读比较拟议改动；如果包含与已确认问题无关的改动，或包含当前档位不需要的改动，就不得把完整 Patch 伪装成单项修复。共同基线本来就属于三个档位，确认该层异常后可以调用已保存档位的平台安装入口统一处理全部订阅；这不授权档位 1、2 获得档位 3 增强。只有用户明确要求档位 3 或完整安全增强时，才执行档位 3 的全部策略和专项验收。

**macOS 单项配置：** 当前没有公开的通用即时单项写入命令。共同基线问题调用已保存档位的安装入口；与共同基线无关的单项 Clash 配置问题只报告已确认字段和生效边界，不手工编辑订阅，也不得用档位 3 完整增强代替单项修复。

**Windows 单项配置事务：** Windows 当前没有安全的即时单项配置写入路径。客户端运行时不得改当前配置。全局脚本中的共同国内域名直连基线属于三个档位，其他增强仍只属于档位 3；不能借共同基线伪装成无关单项修复。完成诊断后报告已确认问题与生效边界，并等待客户端以后正常加载或刷新。

证据指向浏览器、应用、系统网络或本地缓存时，只修对应层，不顺手改 Clash。证据指向节点或服务端时，不擅自切换节点；说明已经排除的本机因素和用户需要做的最少选择。

Windows 客户端运行时不得修改 `verge.yaml`、`config.yaml`、全局脚本、`profiles.yaml`、用途档位或所有权状态；安装器整批延期，只有客户端本来就未运行时才执行这些写入。不得为了复测触发订阅、节点、代理组或 TUN 切换。当前会话只能完成只读验证，或修复不需要改 Clash 受保护状态的那一层，并如实说明生效边界。

只有故障范围仍局限于单个 AI 服务时才按前置步骤查官方状态。本机无法修复，或其他修复依赖产品当前机制时，先确定问题类别，再在线搜索当前的官方或第一方资料；找不到第一方资料时才补充可靠的技术来源。搜索结果必须与本机证据吻合，并整理成用户可以直接照做的方案，不能只给链接或泛泛建议。

### 解释与完成标准

最终说明按 [policy-core.md](policy-core.md) 的输出格式，只给结果、已完成事项和必要提醒。证据、反证、原因、命令、失败过程和上文的内部结论结构保留在内部，不得把“已确认的主要原因”这类句子直接写给用户；用户主动询问“为什么”或要求诊断报告时，才用日常语言依次说明结论、两到四项关键观察、处理动作、复测结果和仍未知的部分，不堆叠术语或可能性列表。

完成条件由任务合同中的交付类型决定：

- **分析或复核：** 结论状态、关键证据、反证、恢复归因和未知项完整；分析或复核任务不要求执行修复或复测。
- **修复：** 修改针对已确认问题，原始症状已复测，受影响的档位能力没有变坏；事务状态必须明确。若本次修复涉及网络配置写入，还必须通过 [profiles-and-patch.md](profiles-and-patch.md) 的强制完成闸门。
- **更新：** 全部远程订阅完成更新前备份、候选检查、现行 Patch、运行加载、已保存档位的全部 `required_followups` 与验收，以及最终状态和自动更新关闭复查；任一步失败时已经恢复原订阅和原运行配置。
- **监测：** 采集器已经确认运行，时间窗、范围和停止方法明确；仅给出命令不算建立监测。

历史问题已经消失且无法重现时，分析任务按现有证据完成，不能伪造修复或复测；修复任务则不能写“已解决”。任一必需条件缺失时继续本机仍可安全完成的工作，只有完成或遇到真实阻塞才收尾。状态回执不能代替完整交付。
