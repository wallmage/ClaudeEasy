## 支持范围

支持：

- macOS 上使用 Mihomo 内核的最新版 ClashX Meta；
- Windows 上使用 Mihomo 内核的最新版 Clash Verge Rev。

要求 Mihomo 1.19.27 或更高版本。旧版 ClashX、旧版 Clash Verge、找不到内核、版本过旧或无法确认内核能力时只检查，不修改。macOS 建议升级到 ClashX Meta；Windows 建议升级到 Clash Verge Rev。

绝对不要退出、停止或重启 Clash 客户端。不得执行、建议或要求用户执行这类操作。中国用户通常依赖客户端越过 GFW；关闭客户端会让 AI 助手断线，并可能让修复停在一半。

## 模块选择

ClaudeEasy 有两个独立模块：

- **Patch** 负责首次安装、用途变化或用户明确要求的网络配置，只应用满足已选用途所需的最少改动。
- **Diagnostics** 负责从用户的模糊描述出发，主动取证、解释、单项修复并复测。

用户说“网络不对劲”时先进入 Diagnostics。不能因为用户提到 Clash、DNS、代理或某个网站，就直接运行安装程序。单项 Clash 配置问题也留在 Diagnostics；只有档位 3 或用户明确要求完整安全增强时才运行完整补丁。

在 Diagnostics 中，只有用户明确要求完整安全增强时才进入 Patch；单纯报告故障不能视为用途选择。

## 用途档位

### 选择与保存

首次在一台电脑上进入 Patch 时，先读取本机档位。macOS 固定保存于 `~/Library/Application Support/ClaudeEasy/usage-profile.plist`，安装和卸载不得接受环境变量把这个内部状态文件改到其他位置；Windows 保存于 Clash Verge Rev 应用目录中的 `claude-easy-usage-profile.json`。两个文件都只记录版本和数字档位。没有已保存档位时，必须先问“你使用网络代理主要用于哪些用途？”，展示以下三项及改动差异，得到选择后才保存和修改。

用户明确说要配置 Claude 或 Claude Code 时，该表达本身就是档位 3 的选择；明确说要配置 ChatGPT、Codex、Gemini、Perplexity 等其他海外 AI，且排除 Claude 时，就是档位 2。

用户可以随时改档。升档只增加新档位所需能力。从档位 3 降到档位 1 或 2 时，先读取并记录旧档位，再运行对应平台的安全卸载程序，最后保存和执行新档位。安全卸载成功后清除旧用途档位；卸载失败或返回 `partial` 时必须保留，不能绕过未完成的恢复。只撤销能确认由本工具写入、且之后没有被用户或客户端继续修改的部分；不能为了降档覆盖后来产生的用户改动。macOS 只有从已开启改为关闭时才写订阅自动更新所有权状态；卸载时当前值仍关闭才恢复为开启，用户已经恢复、原本已关闭或没有状态时不写。所有权使用仅追加事件记录：`prepared`、`installed` 表示仍有恢复责任，`released` 表示已经没有所有权；状态文件保留时也必须按最后一条完整事件判断，不能按文件是否存在判断。中断的最后一条事件可在下次追加前截掉；追加失败只能留下可忽略的残段，不得重写已经同步的有效前缀。追加前后必须核对同一文件身份，不能覆盖并发替换。首条所有权记录先在同目录私有临时文件中完整同步并设好权限，再以不可覆盖的原子改名发布并同步父目录；目录同步失败就停止，成功前不得写 ClashX Meta 的 `defaults`。安装文件删除、自动更新恢复和所有权语义释放必须属于同一个可恢复事务；任一步失败或进程中断时，同时恢复用途档位、自动更新关闭状态和所有权。Windows 按远程 uid 保存原来为开启或缺少字段的项目，原本关闭的项目不纳入所有权；卸载只恢复仍为 `false` 的自有字段，保留用户已恢复的值、本地项目与无关元数据。macOS 已写入当前订阅的内容不能凭猜测还原；Windows 客户端运行时也不会改写应用设置。因此旧订阅增强仍可能保留，必须明确告诉用户“新档位已保存，但这部分旧增强仍保留”，不能伪装成已经恢复。

macOS 三个档位的关闭操作遇到已有 `prepared`/`installed` 所有权时都必须原位完成或续写，不得先写 `released` 再建立新所有权。首次安装时，Shell 在启动关闭子进程前登记回退责任并暂存 TERM、HUP、INT；普通失败先恢复自动更新，确认成功后才恢复旧档位。已有保存档位时保留关闭状态；回读或恢复失败时返回 `partial`，使下次按同一档位继续。

Windows 存在应用设置恢复状态时，安全卸载必须把客户端未运行作为整批文件事务的提交条件。在全部目标句柄和原字节核对完成后、发布事务记录和执行写删前再次检查；若客户端在候选或备份生成期间启动，返回 `partial`，保留全部受保护文件、用途档位和恢复状态，等待以后客户端未运行时重试。

Windows 三个档位安装、备份恢复和卸载中所有要求客户端未运行的文件事务，都必须在全部目标句柄和原字节核对后、发布事务记录前再次检查客户端状态。此时检测到客户端启动，必须在任何受保护写入前拒绝提交并清理事务新建目标、准备记录和事务记录；不能只依赖候选生成前的一次检查。

Windows 安全卸载在读取安装、自动更新和用途档位状态之前，先检查安全更新清单。存在尚未验收的清单时返回 `safe_update_pending`，不得改动或删除全局脚本、用途档位、自动更新与安装状态、订阅、备份或清单；先运行 `-VerifySafeUpdate` 完成整批验收或恢复，再重试卸载。

macOS 卸载暂存目录分为未就绪、就绪和已提交三种状态。未写出 `READY` 时不得删除任何目标，后续运行直接丢弃不完整暂存；写出 `READY` 后的恢复只能把完整暂存文件原子发布到仍为空缺的目标，不能覆盖并发创建的文件。恢复发布本身被强制结束时，目标必须保持“完全不存在”或“完整原文件”两种状态，下一次运行可继续处理其余目标。

用途档位文件、卸载暂存文件与元数据必须先同步文件内容，再同步父目录。安全卸载只有在全部暂存项和 `READY` 都完成同步后才能删除安装文件；删除后必须同步安装目录，失败时恢复全部暂存项并再次同步。首条自动更新所有权记录先在同目录私有临时文件中完整同步，再用不可覆盖的原子改名发布并同步父目录，不能在正式路径留下空文件或半条记录。

macOS 普通安装、安全更新、安全卸载和变更型 Ruby 入口共用备份目录中的私有跨进程操作锁。锁覆盖用途档位读取与匹配、初始快照、自动更新所有权、订阅事务、卸载暂存、最终核对、删除和提交；Ruby 直接变更入口必须先取得同一把锁，Shell 与 Ruby 子流程必须验证继承的描述符、固定锁文件身份及锁仍被实际持有，不能只信任环境标志。普通 Patch 和安全更新的显式档位必须在锁内、任何下载或写入前与固定 `usage-profile.plist` 一致；不一致或无有效档位时零配置写入。自动更新修改子命令只允许已验证外层锁的安装、卸载和恢复流程调用，卸载中断恢复还必须验证 `READY`、所有权标记和暂存的用途档位文件。另一个写流程占用时最多等待 5 秒，随后不修改任何状态并返回 `operation_in_progress`。内部 Ruby 配置锁仍保护单次文件事务，不能代替公开流程锁。这样卸载核对旧文件后，安装器不能在删除前发布新的用途档位或所有权状态。卸载在 `READY` 后被强制结束时，下一次普通安装或安全更新必须先在同一把锁内调用公开卸载流程完成恢复和卸载；自动更新已处于本工具拥有的关闭状态时，恢复返回 `already_disabled_owned` 也必须作为幂等成功继续。只有结构正确的成功收据且暂存目录已经清除，才能继续选择和写入新档位，否则保留恢复状态并返回 `uninstall_recovery_failed`。

macOS 安全卸载发现未完成的配置事务时，必须先恢复原文件并重新加载当前原订阅，依次完成缓存、TUN、代理组、DNS 和连接检查。恢复失败时，在删除安装文件、清除用途档位或恢复订阅自动更新之前返回 `profile_transaction_recovery_failed`，并保留配置事务、用途档位和自动更新所有权；不得把文件恢复冒充运行状态恢复。

### 三档行为

| 档位 | 用途 | 必须做 | 明确不做 | 验收 |
| --- | --- | --- | --- | --- |
| **档位 1｜普通浏览** | 国内网站、Twitter、Facebook、YouTube 等 | 给当前存储位置中的全部订阅安装共同国内域名直连基线，关闭订阅自动更新；用 Computer Use 确认 Clash 客户端的“设置为系统代理”已开启 | 档位 1 不修改 TUN、IPv6、WebRTC、AI 分组或节点 | 国内站、Google、Twitter 和一个用户常用站点能稳定打开，速度无明显异常 |
| **档位 2｜海外 AI** | ChatGPT、Codex、Gemini、Perplexity 等，不含 Claude | 继承共同国内域名直连基线，保持订阅自动更新关闭；用 Computer Use 开启 TUN，并关闭 Clash 客户端自己的系统代理开关 | 档位 2 不增加 WebRTC 或 AI 分组补丁，不修改节点 | 国内站、Google、Twitter、ChatGPT、Gemini 能稳定打开；命令行或 Agent 应用能联网 |
| **档位 3｜Claude/Claude Code** | Claude 网页、Claude Code，或需要完整泄漏防护 | 先完成档位 2，再运行完整补丁 | 不自动选择订阅、代理组或节点 | 完成普通站、其他 AI、Claude、分流、DNS 深度测试和两项 WebRTC 测试 |

档位 2、3 关闭系统代理的目的，是避免 Clash 同时用系统代理和 TUN 重复接管同一流量，不是为了隐藏代理。只关闭 Clash 客户端自己的系统代理开关；除下述 AdGuard for Mac 已知兼容路径外，不得清除或覆盖 AdGuard、其他 PAC、企业代理或安全软件的设置。不能用 `networksetup`、注册表或系统代理命令把其他产品的配置抹掉。

三个档位都包含共同国内域名直连基线。档位 3 的其余完整补丁包括：TUN、DNS 劫持、自动与严格路由、IPv6 关闭、普通国外与 AI DNS 分流、AI 分组与规则、全局 UDP/WebRTC 防护和完整验证。节点只给建议：台湾家宽优先，其次日本家宽；不得自动切换节点。全局 UDP 也会影响 QUIC、游戏、语音和视频，必须在选择界面说明。

macOS 用 `bash scripts/install_macos.sh --profile N` 保存档位，Windows 用 `.\scripts\install_windows.cmd -UsageProfile N`。三个档位都先检查 Mihomo，关闭订阅自动更新，并安装共同国内域名直连基线；档位 1、2 完成后结束，不增加 TUN、IPv6、WebRTC 或 AI 分组设置。Windows 三档都安装全局脚本，脚本内写入数字档位；档位 1、2 只执行共同基线，只有档位 3 继续执行其余完整补丁。自动更新设置由安装程序直接修改，不依赖 Computer Use：macOS 把 ClashX Meta 偏好项 `kAutoUpdateEnable` 写为布尔假值并立即回读；Windows 把 `profiles.yaml` 中每个 `type: remote` 项目的 `option.allow_auto_update` 写为 `false` 并逐项回读。任一平台无法安全识别、备份、写入或确认时，停止且不继续打补丁。

### 档位 3 的 Claude 区域指纹检测

档位 3 必须用随 Skill 安装的 `assets/claude-region-check.html` 完成修改前后两次检测。它是单文件离线页面，用 CSP 禁止联网，支持 Safari、Microsoft Edge 和 Google Chrome。页面给出的是区域指纹参考分，不是 Claude 官方判定；它不检测 DNS、WebRTC 或 TUN，也不能作为 Claude 是否可用的通过条件。选择档位 3 已授权打开本地检测页，不需要再为初检单独确认。

1. **修改前基线：** 在任何系统设置或网络修改之前，从当前 Skill 根目录解析 `assets/claude-region-check.html` 的绝对路径，优先识别用户实际打开 Claude 的浏览器，用 Computer Use 在同一浏览器中打开本地文件；无法确认时才使用系统默认浏览器并明确记录限制。正式支持 macOS 的 Safari 或 Chrome、Windows 的 Edge 或 Chrome；其他浏览器能正常完成初检就记录实际检测结果，不能运行时保持“未验证”，并把兼容性限制纳入第一次授权。不得借用其他浏览器的信号，不得合成一个现实中不存在的指纹。路径含空格时必须作为完整本地文件地址打开，不能把 macOS 路径照搬到 Windows。不得使用 Codex 内置浏览器，也不得用命令行请求替代。点击“开始检测”，每 2–5 秒读取页面状态，最多等待 60 秒；超时后只刷新一次并重试，再次超时就记录“未验证：检测页超时”。本地文件缺失、不可读、JavaScript 被禁用或页面报错时记录“未验证：本地检测页不可用”。检测结束后向下滚动查看九项信号，记录时间、浏览器、参考分、每个非零信号、“有限信息”和“无法读取”项；“命中”只按信号分达到上游 `0.25` 门槛统计，低于门槛的非零贡献仍照实记录。Safari 没有 Chromium 的 `userAgentData`、Windows 桌面浏览器没有提供设备型号时，设备项显示“有限信息”不等于失败。无法读取项必须显示“未知”贡献，不能当成 `+0`；只要存在无法读取项，页面隐藏总分并显示已知项合计和未知权重。没有 Computer Use 时只能让用户在系统浏览器中手动检测，状态保持“未验证”。
2. **一次申请权限：** 浏览器语言只对明确的 `zh-CN` 或 `zh-Hans` 计分；英文、繁体中文和通用 `zh` 仅展示，不计分。系统时区、浏览器语言与 Intl 区域设置、当前用于 Claude 的国产浏览器/WebView 都是可选调整项。先保存四项修改前快照，只汇总实际命中的项目、旧值→建议值和影响，向用户一次申请权限，并明确说明“这些调整只降低参考分，不保证改变 Claude 判定；是否应用？”用户只回复“同意”且没有语言偏好时，默认使用繁体中文：时区用 `Asia/Taipei`，浏览器语言用 `zh-TW`，Intl 使用台湾区域设置。用户明确要求英文时，浏览器语言用 `en-US`，Intl 使用美国区域设置，时区仍用 `Asia/Taipei`。浏览器语言不能只改界面显示：把目标语言放在首位，移除 `zh-CN`、`zh-Hans` 等简体中文语言项；通用 `zh` 不得排在目标语言之前，浏览器在 `zh-TW` 后自动追加的 `zh` 可以保留。台北与北京、上海同为 UTC+8，不会改变当前时间，但时区标识会改变；语言还可能影响浏览器界面和网页内容，区域设置会影响系统和其他应用的日期与数字格式。用户拒绝的项目不得修改。
3. **国产浏览器处理：** 只说明当前用于 Claude 和检测的浏览器或 WebView 会被识别，不把“安装过某个浏览器”当作命中。可以建议用户改用 Safari、Chrome 或 Edge 打开 Claude，但不得仅为降低参考分修改系统默认浏览器。只有用户明确要求更改系统默认浏览器时才执行，不卸载原浏览器。
4. **明确保留与端点分类：** 不得删除中文字体；浏览器可见中文字体和国产厂商字体都保留。国产品牌设备不改，不得伪装设备或 User-Agent。`Asia/Taipei` 仍是 UTC+8，时区偏移不会因此改变；不得为了降分改变实际时钟。Emoji 平台推断只按 User-Agent/平台信息提示，不声称真的检测了渲染。只读分类 `ANTHROPIC_BASE_URL` 时先判断是否设置，再按 URL 解析结果依次判断：未设置为“默认端点”；解析失败、非 HTTPS 或包含 userinfo 为“端点配置异常”；只有 hostname 规范化后精确等于 `api.anthropic.com`、使用默认 443 端口且不得包含 userinfo 时才是“官方端点”；其余合法 HTTPS 地址为“自定义端点”。只报告类别，不得输出完整 hostname，也不得自动更换服务端点。
5. **修改与网络补丁：** 只用 Computer Use 或操作系统提供的受支持界面完成用户同意的系统时区、浏览器语言、Intl 区域设置；用户另有明确要求时才修改默认浏览器。修改后逐项回读确认。若浏览器明确要求重新启动且可能中断工作，另行征得用户同意。本批设置任一步或最终验收失败时，只在当前值仍等于本轮写入值时按修改前快照恢复；用户在期间继续修改过的值不得覆盖。随后运行平台安装程序，完成档位 3 的 TUN、DNS、WebRTC、分流和站点验收。
6. **重新扫描：** 回到修改前实际用于 Claude 的同一浏览器。原检测页仍在时直接点击“重新扫描”，不要先刷新；页面被关闭或必须重开时，重新打开本地页并点击当前可见的“开始检测”或“重新扫描”。按修改前基线的 60 秒规则等待；检测进行中不能反复点击，也不能点击保存、分享或复制结果图片。只有两次扫描都完整，或无法读取项集合完全相同，才比较数值；覆盖范围不同时分别报告已知项合计和未知权重。任何非零项都照实报告，不能据此宣布档位 3 成功或失败。

复测后按非零信号重新分类，只继续处理用户已经同意且可恢复的项目。不得用删字体、伪装设备、改 User-Agent、改变实际时钟或换用 Codex 内置浏览器追分。区域指纹页不能替代 DNS、WebRTC、分流和 Claude 联网验证，也不参与这些网络验收的通过条件。

## Diagnostics 模块

### 工作目标

用户不需要会看日志、懂网络术语或先判断问题属于哪一层。代理负责选择工具、读取本机证据并推进调查；不要求用户先知道该查什么。除下一节规定的 AI 服务官方状态检查外，任何外部记录都不是诊断前提，用户主动提供时才作为补充证据。

**解决原始问题是 Diagnostics 的结束目标。** 只读检查是第一阶段，不是交付结果；诊断结论不是完成，解释和建议不算修复，状态说明不能代替行动。没有证据不能下结论，也不得直接执行 Patch 模块；先保留当前网络、客户端和应用状态，确认需要修改后做与证据对应的最小改动，并持续修复、复测、继续迭代。只有问题已经解决或遇到真实阻塞，Diagnostics 才能结束。

代理不请求用户确认诊断方案。已有授权、当前档位与产品边界内的本机检查、可恢复修复和复测由代理连续完成。只有工具明确要求的操作时确认、缺少密码/MFA/实体操作、下一步会超出当前档位或用户授权、存在不可恢复的数据风险，或受支持工具与外部服务确实不可用时，才向用户提出一个精确的阻塞问题。提出前完成全部不需要确认的准备，只说明待执行动作、影响和恢复方法；用户授权后直接继续，不重复方案。不得把“请回复继续”当成常规收尾。

### AI 服务状态前置检查

用户报告 OpenAI、Anthropic 或其他 AI 服务无法连接、反复重连、流式响应中断、超时、明显变慢或服务错误时，任何本机诊断之前都先确定服务提供商，并查询对应提供商的官方状态页和事件历史。OpenAI 使用 [https://status.openai.com/](https://status.openai.com/)，Anthropic 使用 [https://status.anthropic.com/](https://status.anthropic.com/)；其他服务只使用它自己的官方状态渠道。这一步先于用途档位、本机配置、节点、DNS 和日志检查。

记录查询时间、用户故障时间窗、事件开始和结束时间、当前状态、受影响组件及匹配程度。事件时间和组件都吻合时标为“有力支持”，不能自动把用户的每次失败都归给服务端；没有官方事件也不能排除区域性、账号、模型或尚未公布的异常。完成前置检查后继续当前档位允许的必要本机核对；官方事件已经足以解释症状时，不把改动本机配置当作默认动作。

### 与用途档位联动

用途档位同时约束 Patch 和 Diagnostics。用途档位是 Diagnostics 的需求边界，不只是首次安装参数。每次诊断先读取已保存档位；没有档位时先完成用途选择。把档位转换成三项约束：用户需要保持的能力、本次禁止触碰的设置、修复后必须复测的能力。故障本身不能自动升档；只有用户明确增加用途时才保存新档位，并按新档位重新确定范围。

- **档位 1：** 目标是国内域名稳定直连、普通境外网站可以通过系统代理稳定浏览。维护共同国内域名直连基线，但不检查或修改 TUN，不运行 DNS 泄漏、WebRTC 或 AI 检查，也不查看或修改 AI 分组、Claude 规则和第三档订阅增强。
- **档位 2：** 继承共同国内域名直连基线，目标增加 ChatGPT、Codex、Gemini、Perplexity 和 Agent 联网，并保持 TUN 开启、Clash 自己的系统代理关闭。可以在症状相关时检查 TUN 和 Agent 连接；档位 2 不运行 DNS 泄漏、WebRTC 或 AI 分组检查，也不安装或改写第三档订阅增强。
- **档位 3：** 诊断同时照顾普通浏览、海外 AI、Claude/Claude Code，以及档位 3 的既有能力。修复只涉及浏览器或单个应用时，复测原始症状和受影响能力；修改系统代理、过滤器、TUN、DNS、路由、Clash 或其他共同网络路径时，除原始症状外，必须只重测可能受本次改动影响的第三档能力，并在无法确认时保留“未验证”，不能为了修一个问题破坏泄漏防护或 AI 分流。

诊断报告开头记录当前档位和本次范围，结尾分别报告原始症状与档位回归结果。没有执行某项高档位检查，是遵守用户选择，不是遗漏或失败。

### 通用工作循环

1. **把描述变成可观察的症状。** 从用户原话中提取目标、动作、开始时间、频率和预期表现。能从当前窗口、应用、截图、系统状态或日志自行确定的信息直接读取，只在缺少登录、实体操作或不可推断的用户选择时提一个简短问题。
2. **记录修改前基线。** 始终记录时间、操作系统、活动网络和原始症状，同时记录已保存档位。有 Computer Use 且症状能在界面看到时，必须用用户实际使用的应用、账号、目标和动作在修改前复现；`curl`、配置检查或另一个浏览器只能作为分层证据，不能替代原场景。无法复现时保持“尚未证实”，不得写“已修复”。只有当前档位允许，并且只有影响范围或证据指向共同网络路径时，才读取对应的 Clash 客户端与 Mihomo 状态。不得输出密钥、订阅地址或完整节点地址。
3. **复现并缩小影响范围。** 优先复现用户的原操作。用范围矩阵判断是单个目标、一个应用、当前设备、当前网络还是共同路径：至少包含异常目标的单变量开关对照，以及至少两个健康对照在可疑组件开启时的表现。只有异常目标受影响时，先查目标与组件的交互；健康对照也出现同类故障时，才检查、修复或替换共同组件本身。一个应用异常而其他应用正常时先查应用层；多个应用同时异常时，再向系统、Clash 和网络层推进。相同服务不等于相同账号、接口或认证方式，对照成立前必须确认真正保持不变的条件。
4. **建立假设表。** 每个候选解释都记录支持证据、反证、下一项最便宜的验证和状态。状态只能写成 **已确认**、**有力支持**、**尚未证实** 或 **已排除**。单个现象或相关性只能算线索；关键判断至少需要第二种独立证据，并且必须主动寻找反证。
5. **按需取证。** 按现象选择必要层级，不是每次全部执行。每完成一项检查，都更新假设的状态和优先级，保留所有尚未证实的解释，再选下一项最有区分度的检查。只有充分反证能排除某项解释时，才能标成“已排除”。
6. **检查解释是否完整。** 结论必须能解释全部已知现象，包括成功的对照、失败时间、范围和可量化差异。解释不了的观察必须保留，不能为了收尾而忽略。
7. **修复并迭代。** 一次只改变一个变量，保留修复前的状态和恢复方法。配置缺陷不等于故障原因；与原始症状无关但值得保留的增强必须单独说明，不能冒充修复。能在本机安全修复且属于用户要求的，由代理自动完成；需要管理员权限时由工具发起授权，不让用户抄命令。一次失败不是停止条件：修复失败后恢复原状态并继续取证，按新增证据选择下一项单变量修复。关闭应用、注销账号、删除或隔离缓存、Repair、重装或降级可能影响未保存工作、登录状态或本地数据，执行前必须说明精确对象、备份与恢复办法，并取得明确授权。涉及节点、代理组、订阅或 TUN 时也遵守本项目边界。
8. **针对原始症状复测。** 使用同一原始动作、目标和应用比较修改前后结果，并检查健康对照没有变坏。间歇性问题要覆盖足够长的观察窗口；没有再次复现时写“暂未复现，观察中”，不能写“已修复”。

如果连续两次假设或修改没有改善原始症状，立即执行**诊断重置**：停止继续试改，恢复全部未生效的试验，重新列出已确认、已排除和未知项，并从原场景重新测量各层时间线。诊断重置后继续收集最有区分度的新证据；没有新的证据不得进行第三次修改。不得把前两次失败当成继续猜第三个设置的理由，也不得把诊断重置当成停止工作的理由。

### 因果判定门槛

凡是准备把伴随事件、设置、进程、设备、节点或服务写成反复故障的“主要原因”，必须先完成以下记录，缺一项就不能升级结论：

1. **事件真实性：** 从原始来源识别真实事件并人工抽查样本。日志里的原始事件与引用、摘要或诊断文本必须分开；解析器命中一个错误字符串不等于发生了一次错误。
2. **时间方向：** 候选原因必须先于症状，并落在事先定义的合理窗口内。症状之后发生的事件不能倒算为原因，也不能看完数据后不断扩大窗口去凑匹配。
3. **两个分母：** 在同一可比时间范围内统计全部候选事件和全部故障。候选事件命中率是“候选事件后发生故障 ÷ 全部候选事件”；故障覆盖率是“故障前存在候选事件 ÷ 全部故障”。不报告分母的次数没有因果解释力。
4. **正反例：** 同时列出“有候选事件但没有故障”和“没有候选事件却发生故障”。反例占多数，或候选解释不了大部分重复故障时，最多保留为偶发触发条件，不能称为主要原因。
5. **证据独立性：** 多个记录如果只是同一个下游现象的复制、转述或派生，就不能算两种独立证据。独立证据必须从另一条因果路径支持候选原因与症状之间的上游联系。
6. **单变量干预：** 在其他条件相同的情况下只加入、移除或替换候选原因，重复触发与恢复原始症状。无法安全执行单变量干预时，必须用一条直接记录上游失败的独立证据替代；否则状态只能是“有力支持”或“尚未证实”。

机制解释只能说明为什么可能发生，不能补足实测证据。投入时间、用户要求唯一答案、已经公开过某个判断或终于找到一个说得通的故事，都不能降低因果判定门槛；证据不足时继续取证或如实保留未知项。

结论必须使用以下固定结构：

| 状态 | 结论措辞 |
| --- | --- |
| 全部门槛通过 | `已确认的主要原因：X`，随后列最关键证据和复测结果 |
| 尚缺任一门槛 | `下一项验证：X（有力支持/尚未证实）；尚缺门槛：……` |
| 反证充分 | `已排除 X 作为反复故障的主要原因`，并保留尚未排除的有限作用 |

未确认候选不得称为“最可能的主因”“首要原因”或同义词，再附“尚未确认”也不合格。只有 X 已排除且 Y 已确认时才能写“不是 X 而是 Y”；不能用排除一个错误解释来证明另一个候选。

### Computer Use 与 Sub Agent

Windows Computer Use 已在 2026-07-09 发布的 Windows 桌面版 Codex 中提供；它与 macOS 一样可以看界面、点击和输入，但 Windows 只能操作当前会话的前台桌面，设备必须保持解锁，不能操作 UAC、管理员认证或系统安全授权窗口。开始前必须确认当前会话确实提供并启用了 Computer Use；产品支持不等于当前账号、地区或管理员策略一定开放。macOS 与 Windows 只要当前工具可用，就执行同一类 Clash 客户端开关、浏览器复现和泄漏测试；每次操作后重新读取界面确认。没有工具时如实写明并提供最短的手动步骤，不能伪造验收结果。能通过文件、脚本或结构化接口可靠完成的事情仍优先使用脚本，不为展示自动化而调用界面。参考：[OpenAI 2026-07-09 桌面版发布说明](https://openai.com/index/chatgpt-for-your-most-ambitious-work/)和[当前 Computer Use 文档](https://learn.chatgpt.com/docs/computer-use)。

预计超过 10 分钟、步骤很多，并且至少有两路彼此独立的只读证据时，可以启用多个 Sub Agent。主代理先读取用途档位、定义问题范围和统一时间窗，再按应用界面、Mihomo 连接、系统网络或日志来源拆分任务。Sub Agent 只返回带时间戳的脱敏事实、反证和未知项，不读取或输出订阅地址、密钥与完整节点地址，不运行安装、卸载、订阅更新、配置恢复或任何写入命令。整个任务同时只有一个界面操作者和只有一个主动流量生成者，避免抢鼠标或让并发测试污染计时和连接记录。所有写入、更新、恢复和最终判断都由主代理串行完成。短任务、同一界面操作、同一文件事务或互相依赖的步骤不得为了形式而拆分。

### 判断防线

| 容易误导用户的想法 | 必须执行的动作 |
| --- | --- |
| “命令行很快，页面应该已经好了” | 回到用户实际应用，用 Computer Use 验证原始动作。 |
| “这个配置确实不理想，所以就是它” | 把配置问题与当前故障分开；先做单变量对照和寻找反证。 |
| “关掉一个网站的过滤后变快，整个过滤器都坏了” | 完成范围矩阵；不能因为单个目标的对照结果就停用或删除整个组件。 |
| “又发现一个慢网站，再加一个例外” | 测试至少两个健康对照；同类故障跨目标出现时修共同组件本身。 |
| “前两次没用，再试一个设置” | 诊断重置；没有新的证据不得进行第三次修改。 |
| “这次打开挺快” | 对无副作用场景用同一应用、目标和动作连续测试三次。 |

如果现有记录覆盖不到异常时段，自动建立有开始时间、结束时间和采样间隔的观察窗口。必须记录采集工具或会话、进程或任务标识、采集范围、开始与结束时间、停止与清理方法，并确认采集正在运行。优先记录计数、时序和连接元数据；除非更轻量的证据不足且用户已授权，不抓取通信内容。问题再次出现后，按时间线关联证据并关闭观察，不让监测无限运行。工具无法持续运行时写“未建立监测”，不得承诺下一次会自动采集。

观察时长由原始故障决定。可以立即重复的问题，修复前后各连续测试三次。间歇性问题优先覆盖最近记录中的典型复发间隔；捕捉到一次异常后，修复后至少观察同样长的时间窗。没有历史可参考时先建立短窗口，仍未出现就按用户描述的频率延长，并保持“观察中”。

连续复测不得增加账号或业务风险。重复动作会提交登录、支付、发消息或其他有副作用的请求时，先检查失败次数、限流、验证码和锁定风险；出现迹象就停止重复提交，改用日志、只读接口或无副作用对照。Computer Use 可以读取界面并执行不含敏感输入的步骤；密码、验证码、MFA 或硬件确认由用户完成，代理不得记录或转述。

### 证据选择

以下是可选证据层，不是固定清单：

- **应用与浏览器：** 有 Computer Use 时必须用它重现操作，读取可见错误、加载状态和开发者工具中的失败资源。把 DNS、主文档与关键资源的网络耗时、首次显示和加载结束分开记录；主文档很快但页面仍空白时，优先检查脚本、Service Worker 和扩展注入，不得继续归咎 DNS 或 Clash。比较同一目标在另一个浏览器、无扩展窗口或同应用新会话中的表现；怀疑扩展或过滤器时先完成异常目标与至少两个健康对照的范围矩阵。单站对照无改善立即恢复；只有跨目标证据成立时才修共同组件本身。
- **DNS：** 比较系统解析、Mihomo `/dns/query`、A/CNAME、缓存状态和相关 DoH 的结果。只有证据指向解析或 CDN 错位时才清缓存或改 DNS；`DIRECT` 规则本身不能证明解析路径正确。
- **分流与代理：** 从 Mihomo `/connections` 读取目标、进程、命中规则、`rulePayload`、连接链、出站和字节计数。代理内核持有连接只说明流量经过它，不能单独证明是内核发起了业务请求。
- **传输：** 按需要测 DNS、TCP、TLS、首字节和总耗时，以及丢包、抖动、重传、接口错误和可用带宽。网页慢、连接失败和实时音视频卡顿使用不同指标，不能拿一次测速替代原场景。
- **系统与进程：** 查看当前进程、Socket、网卡计数、路由表和实时收发变化，再定位产生连接的应用。先看元数据和时间范围，避免无边界扫描用户文件。
- **历史与日志：** 先锁定异常时间线，再读取相关系统记录和应用日志。通过进程、连接目标、文件更新时间和事件类型定位日志，不按一张预设应用名单搜索。大日志、进程存在或时间接近都只是线索，必须与独立证据交叉验证。
- **泄漏与安全：** 只对档位 3 运行相应网页与连接验证。档位 1、2 用户明确增加泄漏防护需求时，先改为档位 3，再检查和修复；不得因一次故障报告自行升档，也不得把完整补丁验收当成每次诊断的固定步骤。

### 重叠接管与职责分层

多个无关网站或应用都在内容开始传输前等待近似固定时长、随后快速完成时，先按当前档位建立网络接管清单。档位 1 只检查系统代理或 PAC、浏览器内容过滤和与原始症状直接相关的层，不查看 VPN 或 TUN；档位 2、3 在证据指向共同路径时才加入透明代理或内容过滤器、VPN 或 TUN、DNS 过滤器、防火墙和终端安全软件。设置同时开启只能证明存在重叠，不能证明发生冲突；至少取得以下两类证据：原场景的等待与握手超时、重置或假地址处理失败在时间上对应，以及保持其他条件不变时切换一个组件的兼容模式能稳定消除等待。

确认重叠接管后做职责分层：同一流量层只保留一个透明接管者；内容过滤只覆盖浏览器时，可以把它放到遵守系统代理的应用层，让 VPN 或 TUN 继续负责最终分流、DNS 和 UDP；需要覆盖全部应用或特殊协议时，选择厂商支持的其他组合或明确排除范围。具体模式由用户需要的覆盖范围和厂商限制决定，不能把某个产品的兼容开关写成通用答案。

修复验收同时包含三类结果：原始症状在至少三个不同目标上连续复测；广告过滤、证书处理或应用覆盖等原有功能覆盖仍符合用户需要；当前档位中可能受本次修改影响的能力和安全属性保持正常。只有档位 3 才把 DNS 泄漏、WebRTC 和 AI 分流列为安全回归项。删除诊断期间添加的临时站点规则，不逐站添加例外。任何必要项目不通过都恢复修改前的接管模式，并保留“尚未解决”。

### 第一档已知故障：国内请求误走海外

这是三个用途档位共同继承的共享故障，不是某个网站的专用问题。国内网站或国内应用出现间歇性打不开、同步失败、连接被重置或几分钟后自行恢复时，直接检查以下判据：

1. 目标域名存在于受管国内域名数据集；
2. Mihomo 实时连接却命中 `MATCH`、国外规则或海外代理，而不是受管国内规则与 `DIRECT`；
3. 大陆 DoH 与直连得到国内 CDN 且稳定，当前解析或代理出口得到境外 CDN、超时或重置；
4. 至少一个同类国内目标也受共同路径影响，或配置检查证明全部订阅都缺少共同基线。

满足前 3 项即可确认选路错误；第 4 项用于判断影响面，不能为了凑对照拖延修复。修复必须覆盖当前存储位置中的全部订阅，不能只改当前订阅，也不能给 Kimi、欧陆词典或其他单站添加例外。

共同基线由 `policy.json` 的 `cn_domain_provider` 唯一定义：MetaCubeX ChinaMax 的 `cn.mrs`，`type: http`、`behavior: domain`、`format: mrs`、`interval: 86400`。同一提供器同时驱动 `nameserver-policy` 的 `rule-set:<受管名称>` 和路由的 `RULE-SET,<受管名称>,DIRECT`，避免 DNS 判断与连接选路使用不同名单。显式用户域名规则与档位 3 的 AI 规则优先；受管国内规则位于宽泛 `GEOSITE`、`GEOIP`、`RULE-SET` 与 `MATCH` 之前。若默认名称或缓存路径已被用户占用，用 `-2`、`-3` 递增并生成对应路径；只更新能以名称、URL 和受管路径共同确认所有权的条目。

macOS 每次安装按当前档位逐份转换当前存储位置的顶层订阅；档位 1、2 只加共同基线，档位 3 再加完整增强。Windows 三档都安装带数字档位的全局脚本，让每份订阅加载或刷新时使用相同基线。安全更新三个档位都重新应用共同基线。规则提供器由 Mihomo 每天更新，不实现后台订阅监听。

Diagnostics 不需要重新发明排查顺序：逐份核对提供器、DNS 引用和路由引用，再核对活动配置、提供器更新时间、Fake-IP/DNS 缓存和实时 `DIRECT` 连接。当前无法重现应用症状时，只能写“暂未复现”；配置已修复与历史间歇性现象已证实消失必须分开报告。

### 已知证书故障：系统 PAC 所有权、短暂中断与 Fake-IP 重用

应用偶发服务器身份验证失败时，不套用国内分流修复。若统一日志显示 CFNetwork 路径 `uses proxy`、连接到本机 AdGuard 监听端口并出现 TLS 信任错误（如 `-9802` 或 `CERTIFICATE_VERIFY_FAILED`），而当前同一主机的证书链与主机名校验正常，随后同一路径重试成功，先按系统代理所有权冲突、PAC 查询中断或 Fake-IP 重用调查。单独看到 AdGuard、Fake-IP、某个订阅节点或 Clash `ProxyConfigHelper` 活动都不是结论；必须把 PAC 查询、端口所有者、代理配置变更、AdGuard 连接目标和 TLS 失败放进同一时间线。

先读取系统 PAC 地址并确认回环端口由哪个进程监听，再读取 Clash 客户端自己的系统代理状态。档位 2、3 的基础组合是“Clash TUN 开、Clash 系统代理关、AdGuard 自动代理开”。若故障窗口显示 Clash 的 `ProxyConfigHelper` 正在改动或争用系统代理，且 Clash 自己的系统代理确实开启，只通过 Clash 客户端界面关闭它自己的系统代理；保留 Clash TUN、AdGuard 自动代理和 HTTPS 过滤。

Mihomo 使用 Fake-IP 时，再从 AdGuard 日志读取故障连接的应用、目标域名和 `198.18.0.0/15` 目标地址，只输出脱敏后的时间、域名和假地址；同时从 Mihomo 持久 Fake-IP 数据库的只读快照读取该地址当前的反向映射。只有两项同时成立才确认 **Fake-IP 被重新分配**：AdGuard 在失败时把目标域名连接到某个 Fake-IP；同一个 Fake-IP 现在映射到另一个域名。错误域名与证书域名一致是第二项独立证据。不能只凭地址落在 Fake-IP 网段、当前证书已经恢复或刷新成功下结论。

确认后检查运行配置的 HTTP 或 mixed 代理端口，并用监听进程、控制器运行配置和一次代理请求三重确认该端口正在由当前 Mihomo 监听。不得固定假设为 `7890`。记录 AdGuard 出站代理的开关、协议、主机、端口、用户名、证书信任和 UDP 选项；已有的非 Clash 出站代理不覆盖。原状态为关闭时，只通过 AdGuard 界面设置 **AdGuard 出站代理**为 HTTP、`127.0.0.1` 和已验证的 **Mihomo HTTP 代理端口**，用户名和密码留空，证书信任与 UDP 选项保持关闭。这样 AdGuard 通过 HTTP `CONNECT` 按域名把过滤后的请求交给 Mihomo，不再把可能被重用的 Fake-IP 交给下一层。原状态已经是本工具要求且端口仍属于当前 Mihomo 时不重复修改。

修改后用原应用连续复测原目标三次，并复测至少三个无关目标；从 AdGuard 日志确认新连接不再以 `198.18.0.0/15` 假地址作为出站目标，从 Mihomo `/connections` 确认目标域名、规则和连接链正确。再确认 Safari 和 Chrome 的广告过滤、HTTPS 证书处理以及当前档位可能受影响的能力。任一项目失败就通过 AdGuard 界面恢复 AdGuard 原状态；恢复后回读全部记录字段。恢复失败时停止，不继续叠加修改。

禁止按应用调整 AdGuard 过滤范围；应用名单不可穷举，也不能作为产品级修复。Clash TUN 存在时不得把 AdGuard 改为 `Network Extension`。不得点击忽略证书的“继续”，不添加 Apple、iCloud 或单站规则，不得全局关闭 HTTPS 过滤，也不得把当时使用的订阅节点当成原因。不得直接编辑 AdGuard Plist、第三方 PAC 或系统代理。当前无法复现或没有 Fake-IP 重新分配证据时不改出站代理，写“暂未复现，观察中”，不能把当前证书正常写成历史故障已经消失。

### AdGuard for Mac 已知兼容路径

这是 macOS 上 Clash TUN 与 AdGuard for Mac 共存的产品规则，同时用于 Patch 和 Diagnostics。[AdGuard 官方兼容说明](https://adguard.com/kb/adguard-for-mac/solving-problems/big-sur-issues/)也把从 `Network Extension` 改为 `Automatic Proxy` 作为与部分 VPN 或透明代理冲突时的处理方式。该规则只适用于档位 2、3，因为这两档由 Clash TUN 负责最终分流；它不是升档，不增加当前档位之外的 DNS、WebRTC、AI 分组或订阅改动。Clash TUN 存在时不得把 AdGuard 改为 `Network Extension`，禁止按应用调整 AdGuard 过滤范围。档位 1 依赖 Clash 的系统代理，不能让 AdGuard 自动代理再占用同一个位置；Windows 的过滤机制也不同，两者都不能照搬。

Patch 在切换档位 2、3 的客户端开关时同时检查 AdGuard for Mac。检测到 AdGuard 正在使用 `Network Extension`，就记录当前模式和保护状态，通过 Computer Use 只通过 AdGuard 界面切换到“自动代理”，保持 Clash TUN 开启、Clash 自己的系统代理关闭。运行配置使用 Fake-IP、AdGuard 出站代理原本关闭且当前 Mihomo 的 HTTP 代理端口可以按上述三项证据确认时，再通过 AdGuard 界面配置本机出站代理，避免 Patch 刷新后清理 Fake-IP 缓存时让 AdGuard 保留已经重新分配的旧地址。已有的非 Clash 出站代理保持不动并报告未修改。不得用 `networksetup`、defaults、Plist 编辑或脚本改写 AdGuard 与系统 PAC，不得退出、停用、卸载或重启 AdGuard，也不得添加逐站例外。

Diagnostics 遇到多个无关网站都先空白或转圈约 10–30 秒、随后很快显示，并且现场存在 Clash TUN 与 AdGuard `Network Extension` 时，直接把这条已知兼容路径作为第一项单变量对照，不再从零试一串站点规则。仍要在切换前用原应用复现并记录等待时间；不能仅凭检测到 AdGuard 就宣布故障原因。切换后用同一应用和动作连续复测原目标及至少三个无关目标，并确认 Safari 和 Chrome 的广告过滤仍符合用户需要。档位 2 再复测普通 AI 与 Agent 联网；档位 3 只复测本次共同网络路径可能影响的分流、DNS 与 WebRTC 能力。

自动代理只覆盖遵守系统代理的程序，Safari 和 Chrome 等浏览器通常仍会被过滤；非浏览器应用可能不再经过 AdGuard，必须在修改前向用户说明。AdGuard 出站代理只改变过滤后流量交给 Mihomo 的方式，不扩大 AdGuard 的应用覆盖范围。任何原始等待无改善、广告过滤失效、档位能力变坏或覆盖范围不符合用户需要的情况，都要无改善立即恢复 AdGuard 原状态，并继续通用诊断。不能把这个 AdGuard 专用兼容路径写成其他过滤器或 VPN 的通用答案。

macOS 当前流量优先使用 `nettop` 的按进程/连接 CSV、活动监视器的网络计数、`netstat -ib`、系统 DNS/路由状态和 Mihomo 连接记录。macOS 不保证保存一份可直接按应用回放的长期流量历史；历史不足时建立观察窗口，并用相关应用日志补充，不能假装已取得过去的逐应用字节。

Windows 历史总量优先读取 `ConnectionProfile.GetNetworkUsageAsync` 返回的 `NetworkUsage`，按时间粒度汇总 `BytesSent` 与 `BytesReceived`，并覆盖异常期间使用过的全部网络配置；当前网卡使用 `Get-NetAdapterStatistics`。网页分阶段耗时优先使用系统自带的 `curl.exe`，TCP 端口对照使用 `Test-NetConnection`，连续时延和丢包使用 `Test-Connection`；实时应用优先读取应用自己的质量统计。需要捕捉复发问题时，可使用有明确时间和目标范围的 `pktmon` 计数或过滤采集。SRUM 或受保护的逐应用数据只有在确有必要、获得权限且能安全只读时才使用；聚合总量不能冒充逐应用归属。

日志与开发者工具只读取必要时间窗和必要字段。访问令牌、refresh token、ID token、`Authorization` 头、Cookie、客户端密钥、账号标识、会话内容、请求正文和完整本地路径不得写进诊断记录、聊天或搜索请求；能在本机完成的匹配只输出脱敏后的计数、时间、事件类型和结论。

### 判断与修复

禁止把“可能是”包装成结论。代理应优先设计能区分两个候选解释的检查，而不是继续罗列可能性。涉及数量时核对时间范围、单位、累计值与增量值，并检查推导是否能覆盖观察到的数量级；数学接近仍需独立证据确认对象和行为。

证据指向 Clash 配置时，先区分单项故障和完整安全增强。Patch 模块会应用完整安全策略，不是单项修复器，但这只属于档位 3。先只读比较拟议改动；如果包含与已确认问题无关的改动，或包含当前档位不需要的改动，就不得把完整 Patch 伪装成单项修复。档位 1、2 的诊断不得调用完整安装器。

**macOS 单项配置事务：** 留在 Diagnostics，只修改证据确认的字段。保存原始字节和代理组选择；用 YAML 1.2 生成候选；重新读取候选；再次执行相同单项转换并要求无变化；用受支持的 Mihomo 在 30 秒内校验。写入当前订阅后只通过本地控制器刷新，并依次清除 Fake-IP 和 DNS 缓存，再复测原始症状。任何一步失败都恢复原始字节和原运行配置。不得调用完整安装器来代替这个事务。

**Windows 单项配置事务：** Windows 当前没有安全的即时单项配置写入路径。客户端运行时不得改当前配置。全局脚本中的共同国内域名直连基线属于三个档位，其他增强仍只属于档位 3；不能借共同基线伪装成无关单项修复。完成诊断后报告已确认问题与生效边界，并等待客户端以后正常加载或刷新。

证据指向浏览器、应用、系统网络或本地缓存时，只修对应层，不顺手改 Clash。证据指向节点或服务端时，不擅自切换节点；说明已经排除的本机因素和用户需要做的最少选择。

Windows 客户端运行时不得修改当前配置；这里的当前配置是 `verge.yaml`、`config.yaml` 和 Mihomo 正在使用的运行配置。安装器可以更新全局脚本，也可以修改 `profiles.yaml` 中只负责订阅自动更新的字段。补丁内容仍要等待客户端以后正常加载或刷新订阅，此时只能写“已更新，尚未生效”，不能写成已立即生效或“已解决”，也不得为了复测而触发订阅切换、节点切换、代理组切换或 TUN 切换，更不得重启客户端。当前会话只能完成只读验证，或修复不需要改运行配置的那一层，并如实说明生效边界。

AI 服务连接故障已经按前置步骤查过官方状态。本机无法修复，或其他修复依赖产品当前机制时，先确定问题类别，再在线搜索当前的官方或第一方资料；找不到第一方资料时才补充可靠的技术来源。搜索结果必须与本机证据吻合，并整理成用户可以直接照做的方案，不能只给链接或泛泛建议。

### 解释与完成标准

最终说明面向小白，按以下顺序写：

1. **发生了什么：** 一句话结论和证据状态。
2. **证据：** 两到四项最能区分其他解释的观察。
3. **为什么会这样：** 用日常语言解释，术语出现时立刻说明含义。
4. **做了什么：** 自动完成的修复，或本机无法修复时的明确方案。
5. **复测：** 原始症状的修改前后结果和观察时长。
6. **仍未确认：** 缺失证据和观察状态。只有已经确认采集器正在运行时，才说明下一次异常会记录什么；未建立监测时直接说明限制。

完成必须同时满足：结论有证据、修复针对已确认问题、原始症状已复测、没有引入新的异常。任一项缺失就继续本机仍可安全完成的工作；只有问题已经解决或遇到真实阻塞才收尾。报告实际状态不能替代下一项行动，也不能写“已解决”。

## Patch 检查顺序

以下步骤 1–8 用于三个档位的共同国内域名直连基线；档位 3 继续执行完整增强与专项验收。档位 1、2 不执行 TUN、IPv6、WebRTC、AI 分组或第三档验证。

1. 识别操作系统和客户端。
2. 找到客户端配置目录。
3. 先读取客户端当前使用本地存储还是 iCloud，只选择当前存储位置；不得同时扫描两个位置。
4. macOS 只枚举当前存储位置中客户端实际使用的顶层 `.yaml`、`.yml`；排除旧 iCloud 容器、缓存、备份、日志和临时文件。`config.yaml` 是 ClashX Meta 的默认基础配置，不得删除；当前订阅不是 `config` 时安静跳过，只有它本身被选中时才处理。
5. 找到当前订阅和主代理组。
6. 执行带已保存数字档位的平台安装程序；当前存储位置中的全部订阅必须使用同一共同基线。
7. 检查是否移除了旧版危险持久化机制。
8. 当前订阅修改后，通过 Mihomo 本地控制器自动刷新并完成运行检查；失败时恢复原文件和原运行配置。
9. 验证国内目标实时命中受管规则并直连；档位 3 再完成其余分流与浏览器测试。

任何时候都不能输出整份配置。日志只能出现配置显示名称、处理状态、代理组名称和节点显示名称。

## 脚本接口与内部职责

所有公开命令都显式支持 JSON v1：macOS 使用 `--json`，Windows 使用 `-Json`。默认模式继续输出原有中文信息。JSON 模式的标准输出只能有一个对象，不能混入日志；对象中的 `exit_code` 必须与进程退出码一致。`code` 和 `operation` 是稳定的机器标识，`command` 只允许 `install`、`uninstall`、`patch`、`verify_routes`。所有必填字段、状态值和字段类型以 [result-contract.json](result-contract.json) 为准。

JSON 结果必须经过统一脱敏，不得含订阅 URL、密码、UUID、私钥、控制器密钥、完整本机路径或节点名称。Skill 调用脚本时优先使用 JSON 模式，并依据字段判断结果，不解析中文文案。面向用户的默认中文输出同样不得显示敏感值；分流验证只报告代理组已识别和各目标的检查状态，不显示代理组名称、当前节点或连接链节点。

ClaudeEasy 的公开脚本固定在 `claude-easy/`，参数和调用方式保持兼容。内部代码按配置转换、备份与事务、Mihomo 校验、订阅处理、安全更新、运行状态和 CLI 组织；入口只负责参数、编排与结果输出。拆分不能改变事务顺序、安全边界或既有退出码。

## DNS 与 TUN

档位 1、2、3 的共同国内域名直连基线：

```yaml
rule-providers:
  claude-easy-cn-domain:
    type: http
    behavior: domain
    format: mrs
    url: https://raw.githubusercontent.com/MetaCubeX/meta-rules-dat/meta/geo/geosite/cn.mrs
    path: ./ruleset/claude-easy-cn-domain.mrs
    interval: 86400
    proxy: <主代理组>
dns:
  enable: true
  respect-rules: true
  direct-nameserver:
    - https://223.5.5.5/dns-query#DIRECT
    - https://1.12.12.12/dns-query#DIRECT
  direct-nameserver-follow-policy: false
  nameserver-policy:
    rule-set:claude-easy-cn-domain:
      - https://223.5.5.5/dns-query#DIRECT
      - https://1.12.12.12/dns-query#DIRECT
rules:
  - RULE-SET,claude-easy-cn-domain,DIRECT
```

档位 3 的追加策略：

```yaml
ipv6: false
tun:
  enable: true
  stack: system
  dns-hijack:
    - any:53
    - tcp://any:53
  auto-route: true
  auto-detect-interface: true
  strict-route: true
dns:
  enable: true
  ipv6: false
  respect-rules: true
  use-hosts: true
  use-system-hosts: true
```

补丁不创建安全代理组。`DNS` 出站只把请求交给 Mihomo 内部 DNS 模块，不是远端代理。Fake-IP 模式会在连接规则判定前解析域名，因此三个档位都必须让 `nameserver-policy` 与路由引用同一个受管规则提供器，不能只设置 `direct-nameserver`。档位 3 另保留 `geosite:cn` 后备；普通国外查询使用带原主代理组标签的受管 DoH，AI 域名查询使用带 AI 分组标签的同一套受管 DoH。这样国内直连网站获得大陆 CDN，AI 的解析请求和网页连接使用同一个 AI 出口。

两组 DoH 都直接连接解析器 IP，无需先解析解析器域名，避免解析器域名错误引发证书失败。代理侧使用 AdGuard 的两个非过滤地址和 TWNIC Quad 101；直连侧使用阿里 `223.5.5.5` 和 DNSPod `1.12.12.12`。所有查询都使用 HTTPS，不加入广告拦截，不发送 ECS。

`default-nameserver` 和 `proxy-server-nameserver` 属于网络启动边界，必须保留用户值。`proxy-server-nameserver` 缺失时使用 `system`，满足 Mihomo 的 `respect-rules` 要求；如果启动字段等于旧版补丁写入的固定 `1.1.1.1`、`8.8.8.8` 组合，也迁移为 `system`。不得把可直接访问的节点域名解析器替换为可能被阻断的境外地址。

`direct-nameserver` 不保留原值，统一写成策略文件中的大陆 IP DoH；同时把 `direct-nameserver-follow-policy` 设为 `false`。`nameserver-policy` 中的 `geosite:cn` 也必须覆盖为同一组解析器，避免 Fake-IP 初次解析先落到代理侧。这样不会让用户原有的 `system`、明文 DNS 或代理 DNS 使国内域名继续泄露或获得境外 CDN。直连 DoH 会让阿里或 DNSPod 看到国内域名查询，但本地运营商只能看到加密的 HTTPS 连接；这属于受管的分流，不是意外泄露。

如 `nameserver-policy` 把多个域名写在同一个逗号分隔键中，拆成独立键。只有当解析器片段指向已知的非直连节点，或指向依赖关系中无法到达 `DIRECT` 的静态代理组时，才保留这个分流目标；解析器地址统一换成策略文件中的三个 IP DoH。这样不会因为 `dns.google`、`cloudflare-dns.com` 等解析器域名被错误解析而让所有新域名一起失败，也不会继续依赖某些节点会拒绝的 `8.8.8.8`、`1.1.1.1`。DNS 静态安全判断不执行订阅提供的 `exclude-filter`；只要过滤器非空，该组就无法静态证明，解析器改用受管 DoH。带 `use`、`include-all` 或其他动态成员的组同样改用受管 DoH。只有不带过滤器的空静态组，才接受明确指向安全内联代理的 `empty-fallback`；默认的 `COMPATIBLE` 不合格。Mihomo 的 `exclude-type` 只作用于自动纳入的节点，这些动态组本来就不保留。

`#h3=true` 可以保留。除受管的 `direct-nameserver` 外，`#en0`、`#RULES`、未知名称、明文 DNS、`DIRECT`、`DNS` 出站和没有代理组标签的查询都改为代理侧受管 DoH。带 `skip-cert-verify=true` 的解析器跳过证书校验；带 `ecs` 或 `ecs-override` 的解析器会发送客户端子网信息。这三类参数也改为受管 DoH。

不要为某个打不开的网站添加专用 DNS 例外，也不要为测速成绩添加国内 DNS 例外。国内 CDN 错位时检查 `direct-nameserver` 和实时出站，不添加站点规则。同类网站一起出现 `SERVFAIL` 时，应检查整组解析器和当前节点；某个配置在另一节点上恢复，通常是节点故障，不要误改 DNS。最后以真实泄漏测试结果为准。

## 主代理组

主组候选包含 Mihomo 的 `select`、`url-test`、`fallback`、`load-balance` 和 `relay` 代理组。优先按以下顺序选择非 AI、非本工具受管的组：

1. 最后一个 `MATCH` 指向的非 `DIRECT` 代理组；
2. 被宽泛规则（`MATCH`、`GEOIP`、`GEOSITE` 或广域 `RULE-SET`）引用超过一次的代理组；
3. `Proxy`、`PROXY`、`Final`、`Fallback`、`节点选择`、`节点列表` 或 `兜底分流`；
4. 第一个包含代理成员或代理提供者的代理组。

找不到独立主组时，再选择含代理成员或代理提供者的 AI 命名组或本工具受管组；若仍没有，则使用第一个 Mihomo 合法代理组。这样非空且通过 Mihomo 校验的代理组集合总能获得主组，共同基线不会因订阅使用自动代理组或只有 AI 分组而静默跳过。最后选择只发生在代理组之间，不猜单个节点。若主组就是 AI 分组，普通与 AI 流量暂时共用它；不得制造代理组自引用。

## AI 组

先寻找订阅已有的可选 AI 分组。名称匹配策略文件中的 AI 组名称，或包含独立的 `AI`、`OpenAI`、`人工智能` 时，视为已有 AI 分组。已有时直接复用，只补全规则；分组类型、成员、顺序、图标和当前选择全部保持原样。

只有确认没有可选 AI 分组时，才创建 `🤖 AI · ClaudeEasy`。新组直接列出订阅中全部有效的内联代理节点，并通过 `use` 接入全部有效的 `proxy-providers`。不得只把主代理组或“节点列表”作为唯一成员；否则用户无法让普通流量与 AI 流量选择不同节点。名称被其他代理组或内联代理占用时使用没有冲突的编号。重复运行必须复用已创建的组，不能产生重名。没有任何有效内联节点或代理提供者时不创建分组，保持原文件不变并说明原因。

AI 组负责 OpenAI、ChatGPT、Codex、Claude、Anthropic，以及策略文件中列出的 Google AI 和相关服务流量。

## 节点建议

用户原有 AI 分组的成员保持不变。只有 ClaudeEasy 自己新建或旧版创建的 AI 分组会填入全部可用节点和代理提供者。补丁不得调用控制器切换节点，也不得替用户选择台湾、日本或任何家宽节点。

AI 分组的用途是分开普通流量和 AI 流量：主代理组可以选择低倍率节点用于浏览、下载和视频，AI 分组可以由用户单独选择信誉更好的家宽节点。补丁只提供完整选项，不替用户决定。

聊天中说明家宽通常比数据中心节点更适合 AI 服务；如果用户有台湾家宽，优先建议台湾，没有台湾时可建议日本。建议只写在聊天中，最终选择完全交给用户。

## AI 规则

唯一数据来源是 [policy.json](policy.json)。Windows 脚本中的策略块由本地生成器写入，并由一致性测试检查，不能手工维护另一份规则。

规则覆盖：

- `anthropic.com`、Claude 应用、内容、MCP 和静态服务；
- `openai.com`、`chatgpt.com`、Codex 所使用的 OpenAI 域名；
- OpenAI 实时语音、静态资源、上传和明确属于 OpenAI 的验证服务；
- 已有补丁中的 Google AI 和 Gemini 域名；
- Anthropic 官方公布的入站 IPv4 `160.79.104.0/23` 与 IPv6 `2607:6bc0::/48`，并使用 `no-resolve`；
- `DOMAIN-KEYWORD,openai` 后备规则。

明确禁止把以下通用域名整体交给 AI 组：

- `raw.githubusercontent.com`
- `storage.googleapis.com`

不得把整站 `sentry.io`、`auth0.com`、`segment.io`、`intercom.io`、Stripe、Cloudflare Challenge、SendGrid、WorkOS 等共享服务交给 AI 组。只保留第一方域名和能确认专门服务于 AI 产品的精确主机名。
`ai.com` 属于无关产品，也不得加入 AI 规则。

从旧策略升级时，把目标仍是补丁自有 AI 组的 `DOMAIN-SUFFIX,ai.com` 和 `IP-CIDR,160.79.104.0/21` 当作迁移项删除，并写入当前的 `/23`。相同旧规则若指向用户组，必须保留；DNS 中旧的 `+.ai.com` 也只在解析器仍指向补丁自有安全组时删除。

只删除目标为受管 AI 组的上述规则。其他用途的规则保持不变。

订阅把同一批 AI 域名交给主代理组的通用规则必须替换，否则会让 AI 流量绕过独立 AI 分组。用户明确写给其他非主代理目标的同类规则保持原目标，并排在补丁规则之前。AI 明确规则必须出现在国内直连、GEO、所有 `RULE-SET` 和 `MATCH` 之前。

## WebRTC

依次加入两条规则：

```text
NETWORK,UDP,<AI 分组>
NETWORK,UDP,REJECT
```

第一条的目标使用 AI 分组，不创建安全代理分组。把两条都放在规则列表开头，确保更靠后的 `NETWORK,udp,DIRECT`、`DST-PORT,3478,DIRECT`、进程规则和任意 `RULE-SET` 都不能先放行 UDP。已有规则不删除；除了与补丁 AI 规则同键的用户规则会前移以保留优先权，其余规则保持原目标和相对顺序。

AI 分组当前选择必须是代理节点，不能是 `DIRECT`。节点不支持 UDP 时 Mihomo 继续匹配拒绝兜底，不得写成 WebRTC 已验证；它不会因此改走本地直连。补丁不得切换分组或节点，只能检查并如实报告当前状态。

不能按浏览器应用或 AI 域名单独防 WebRTC。同一个浏览器会同时访问国内和 AI 网站，而 STUN 连接的目标与原网页域名分离，Mihomo 无法判断连接来自哪个标签页。TCP 和 DNS 按域名分流；WebRTC 防护必须覆盖所有 UDP。HTTP/3/QUIC 也经过 AI 分组；国内网页的 TCP 与 DNS 仍然直连。在线游戏、语音和视频通话也可能受影响，安装前后的说明都必须写明这个影响。

AI 网页流量、AI 域名 DNS 和所有 UDP 使用同一 AI 分组。多个结果如果全是代理出口，不属于真实 IP 泄漏；单一结果更容易确认。

## 订阅补丁与安全更新

项目不得安装永久监听、后台守护、LaunchAgent、`WatchPaths` 或计划任务来盯订阅变化。三个档位都会关闭订阅自动更新，因此平时没有订阅变化，也不需要轮询。

用户说“更新节点”“更新订阅”或同义表达时，触发一次安全更新。这里的“节点”按用户意图理解为全部远程订阅，不是切换或只刷新当前节点：

1. 读取已保存档位、当前存储位置和客户端记录的全部远程订阅；不输出地址。清单缺失、重复或无法一一对应配置文件时停止。
2. 每次写入前为全部当前配置创建带日期时间的私有备份。第一次运行另存初始快照；不得自动删除历史备份。
3. macOS 在内存中下载全部远程订阅，地址只经标准输入交给 `curl`，不得放进进程参数、日志或错误提示。只接受 HTTPS 成功响应和有效 UTF-8 YAML。
4. 三个档位都对每份候选重新应用共同国内域名直连基线；档位 3 再应用完整补丁，档位 1、2 不得增加第三档字段。全部候选都要经过 YAML 重读、二次转换一致性检查和受支持 Mihomo 校验。
5. 只有全部候选合格且当前文件哈希仍与读取时一致，才在锁内统一替换。任何一份下载、转换、校验、并发检查或写入失败时都尝试恢复全部目标；恢复所有目标后才可写“全部保持原样”。恢复本身失败时继续处理其余目标，并逐份报告未恢复项。
6. 更新后只通过本地控制器刷新当前订阅，保留目标配置中仍存在的代理组选择，清理 Fake-IP 与 DNS 缓存并执行当前档位验收。旧自有分组被候选删除时不再要求它继续存在；候选仍保留的用户 Selector 丢失或改选仍必须失败。运行检查失败时整批回滚；回滚前也要备份当前版本，恢复目标必须匹配预期 SHA-256、真实路径和提交文件身份。运行回退已经恢复当前订阅文件时，整批回退必须把它视为已恢复，继续恢复其他订阅，并报告运行内核仍未恢复；不能再次回退同一文件并误报文件恢复失败。事务在写入前记录真实路径、原 inode、原字节和完整候选；发布前必须同时确认逻辑路径与真实路径都在同一个规范配置根目录内，指向目录外的符号链接必须拒绝。v2 事务中，目标已为完整原字节时只确认，只有同一原 inode 上的完整候选才自动恢复；空文件以及原字节或候选的任何截断前缀都无法判断来源，必须原样保留目标与事务并返回待恢复。不同 inode、重指后的符号链接目标都是客户端或外部流程发布的新文件，即使字节相同也必须保留；文件事务可以结束，只有运行内核仍需恢复时才保留记录和待恢复状态。没有文件身份的旧版事务只在目标已是原字节时结束，否则停止并保留，不能按候选摘要覆盖。若进程在当前订阅加载候选后被强制结束，下一次安全更新先按事务恢复原文件，再通过本地控制器重新加载恢复后的当前订阅、清缓存并验收；运行内核无法恢复时在下载前返回待恢复状态，不能让磁盘与运行内核继续分叉。
7. Windows 运行 `-SnapshotProfiles`，从 `profiles.yaml` 核对每个远程 uid 与本地文件一一对应。读取索引后持续持有索引及全部远程订阅的只读版本锁，先确认当前每份订阅都有非空代理组并通过 YAML、Mihomo，再从锁内同一版本建立脱敏清单和备份、记录客户端的 `updated` 时间戳，最后发布清单才释放锁；客户端写出的 `updated: null` 是合法的空时间戳。Clash Verge Rev 先写订阅文件、后保存索引的更新若已写出订阅但尚未保存索引，订阅必须先通过基线校验；索引写入在版本锁期间失败，只有清单发布后重试成功才能成为本轮时间戳凭据。中间文件不通过校验时不得创建更新前备份或清单。存在尚未验收的清单时必须先完成 `-VerifySafeUpdate`，不能覆盖。再通过 Clash Verge Rev 界面的“全部更新”触发，没有该入口时逐份处理清单中的每一份。之后运行 `-VerifySafeUpdate`，每份订阅必须以文件 SHA-256 变化或比快照更新的 `updated` 时间戳证明本轮已刷新；内容不变但时间戳更新可以通过，两者都不变时保留清单和订阅并返回 `safe_update_refresh_pending`。有刷新凭据后再确认已安装的受管 `Script.js` 与当前安装包及保存档位一致，逐份确认顶层 `proxy-groups` 是至少含一个条目的块状或行内列表，然后做 YAML 与 Mihomo 检查并确认当前档位仍关闭自动更新；缺少代理组或列表为空时不能判成功。通过 Mihomo 校验的非空代理组只会使用当前引擎支持的合法类型，而引擎必须为全部合法类型以及只有 AI 分组的配置选出代理组主目标，不能静默返回原配置。这里不重新实现 YAML 解析器，也不声称在 PowerShell 中执行了用户原脚本或全局脚本；合法性继续由 Mihomo 判断。`profiles.yaml` 映射未变但订阅文件缺失时，必须从清单绑定且哈希匹配的备份原子重建，并与清单删除一起提交；同一路径重新出现时视为并发变化，不得覆盖并保留清单。只有订阅内容缺失或检查失败，且索引与受管脚本仍与检查开始时一致，才允许在持续锁住这两个控制文件时整批恢复；索引、脚本或其他验收状态并发变化时必须返回 `safe_update_verification_retry_pending`，保留当前订阅和清单。订阅本身并发变化时也不得覆盖新内容。旧版 v1 清单可凭内容变化验收，且不再依赖不会用于自动恢复的旧备份；内容没变但当前订阅完整通过检查时，删除旧清单并返回 `safe_update_legacy_snapshot_required`，允许下一次建立 v2 快照。验收失败时不能自动恢复来源无法确认的旧备份，必须返回 `safe_update_legacy_recovery_pending` 并保留当前订阅和清单。只有 v2 一致快照的全部恢复成功后才作废清单。文件恢复不等于运行内核已经恢复，必须把运行状态写成“未验证”并重新读取实时配置与分流；不得把只更新当前一份、只完成界面点击或只恢复文件报告成完成。
8. 三个档位都会关闭订阅自动更新。网络正常时不主动建议频繁更新；连接异常、服务商通知订阅变化，或距离上次更新已数月时，引导用户说：“请帮我安全更新全部订阅”。本次只执行一次获取和更新，不长期重新开启周期自动更新；按已保存档位重新应用补丁并通过验收后，再次确认自动更新关闭。任何一份失败时必须按上述事务恢复，只有确认成功恢复后才说“全部保持原样”。

macOS 安全更新恢复未完成事务时，活动配置必须从当前存储目录的全部顶层配置识别，不能只搜索远程订阅目标；因此活动 `config.yaml` 也必须真正重新加载。旧事务和本次更新回滚都只有在原字节恢复、原配置重新加载、缓存清理和运行检查全部成功后才可删除；运行恢复失败时保留同一记录，下一次 Patch 或安全更新继续处理，且在完成前不得下载或写入新候选。

配置历史用于诊断与回滚：当用户说某次改动后变慢或断网，先列出备份，选择症状出现前最近的一份作为候选，再把当前配置与候选做配置差异比较；只输出字段路径、文件名与 SHA-256，不输出配置值。时间接近只能帮助选备份，不能仅凭时间接近就判定某项变化造成故障。macOS 使用 `--list-backups`、`--compare-backup ID`、`--restore-backup ID --expected-current-sha256 SHA256`；Windows 使用 `-ListBackups`、`-CompareBackup ID`、`-RestoreBackup ID -ExpectedCurrentSha256 SHA256`。恢复前验证备份 YAML 与 Mihomo、核对目标文件和预期 SHA-256，并为当前版本再建备份；恢复后复测原始症状，恢复或运行检查失败时恢复回滚前版本。macOS 备份恢复与 Patch、安全更新共用操作锁，并在读取备份和写配置前先恢复未完成的批量事务；事务恢复改变当前字节时，本次请求按预期哈希冲突停止，必须重新比较。备份事务把提交后的真实路径和文件身份交给运行加载与失败回退；外部以相同字节替换目标也不得覆盖。macOS 恢复当前订阅后必须通过本地控制器重新加载，保持恢复前的 TUN 开关与目标仍保留的代理组选择，并完成缓存、DNS 和连接检查；失败时恢复回滚前版本。文件恢复但运行内核未恢复时必须单独报告；恢复非当前订阅时不得切换当前订阅。Windows 客户端运行时不得为了恢复而停止客户端，只能完成比较并报告当前无法安全自动恢复。

### macOS

macOS 只允许单次显式运行。不得安装永久监听、LaunchAgent、`RunAtLoad`、`WatchPaths`、计划任务或目录监听。用户明确选择新档位时，安装器在平台、客户端、Mihomo、状态路径和初始快照全部通过后，先原子保存新档位作为恢复意图，再修改自动更新或订阅。可捕获的失败必须恢复旧档位；进程被强制结束时保留新选择，下一次 Patch 或安全更新按新档位完成缺失步骤，不得按旧档位重建订阅。

普通 Patch 与安全更新的最终 Ruby 子流程执行期间，Shell 必须暂存 TERM、HUP 与 INT。没有信号且子流程失败时恢复旧档位和自动更新；子流程确认成功时先提交保存档位与自动更新所有权，再以 `partial/operation_committed_interrupted` 处理等待信号。前台进程组信号同时终止子流程、无法确认提交状态时返回 `partial/operation_interrupted_recovery_intent`，保留新档位、自动更新关闭状态和所有权供下次继续。不能在可能已经提交配置后恢复旧档位。

Shell 在最终子流程前创建固定长度、权限为 0600 的 pending 提交收据；Ruby 完成文件与运行配置事务后、输出任何文本或 JSON 前，把同一文件原位改成 committed 并同步。stdout 断开或结果文件写满时，外层核对 committed 收据并返回 `partial/operation_committed_result_failed`。事务已经成功但收据写入、同步或读回失败时，Ruby 必须用不依赖再次输出的内部退出状态通知 Shell，外层同样返回 `partial/operation_committed_result_failed`。收据损坏、不可读或子进程异常终止而无法确认提交状态时返回 `partial/operation_result_unknown_recovery_intent`。以上情况都保留新档位、自动更新关闭状态和所有权；只有收据仍为有效 pending 且子进程普通失败时才恢复旧状态。收据路径必须位于当前备份目录，文件身份、权限、唯一链接、nonce 和 pending 字节不符时拒绝使用。

只处理 ClashX Meta 当前存储位置。使用本地存储时只看本地目录；使用 iCloud 时只选包含当前订阅的当前容器。读不到存储模式，或多个 iCloud 容器无法通过当前订阅唯一判断时停止，不猜。旧容器、历史目录和备份即使仍存在也不得处理。

订阅使用 YAML 1.2 核心类型读取，`yes`、`on`、`0123`、`1:20` 和日期保持文本。多文档 YAML 与循环别名按无效内容跳过；超过系统 Ruby 安全递归深度的文件只跳过该文件，不能终止整批。写入前先在临时文件中生成并重新解析候选，并强制使用满足最低版本的 Mihomo 检查。读取、校验和写入之间若订阅被刷新，重新读取并重试，连续变化时跳过。文件锁必须在固定时间内取得；首次建立状态目录时逐级创建私有目录并同步新目录及其父目录，中途失败后的重试必须先重新同步已出现的目录，完成前不得写恢复状态、偏好或配置。普通安装和安全更新在第一次整批写入前保存持久事务记录，记录逻辑路径、真实路径、原文件身份、原字节和完整候选。发布事务前，逻辑路径与真实路径必须同时位于同一个规范配置根目录；允许的目录内符号链接只写入真实目标并保留链接本身，指向目录外时整批停止。事务记录原子发布后必须同步父目录，且在这一步成功前不得写配置；事务完成后删除记录也必须同步父目录，失败时保留待处理状态。配置通过已锁定的原文件句柄先截零、再写入并同步，因此客户端同时原子替换目标时，新 inode 始终留在目标路径，本次操作检测到身份变化后停止。v2 恢复只自动把同一原 inode 上的完整候选恢复成原字节；完整原字节只确认，空文件和任一原字节或候选前缀都保留目标与事务并返回待恢复。不同 inode 一律保留，不能在无法确认来源的状态上继续。每次写入都使用独占创建生成一个带日期时间的版本化备份，两个进程不能互相覆盖；备份完整写入并设好私有权限后同步备份目录，成功后才允许后续修改。

候选 YAML 重新读取后，必须再次执行完整转换。二次转换仍报告变化，或二次结果与第一次候选不同，说明补丁不具备幂等性；此时保留原文件并写成“已跳过：二次转换不一致”。

当前订阅写入前记录当前所有可选代理组的选择。写入后只允许通过 Mihomo 本地控制器执行 `PUT /configs?force=true`，并要求 HTTP 204。刷新成功后依次执行 `POST /cache/fakeip/flush` 和 `POST /cache/dns/flush`，避免旧 Fake-IP 映射继续使用代理节点所在地的 CDN；任一请求失败都视为刷新失败。

普通 Patch、安全更新、备份恢复和未完成事务恢复必须在每次控制器加载前重新读取 ClashX Meta 的当前订阅，并在自动发现目录时同时重新读取本地/iCloud 存储位置。两次读取、唯一活动路径或开始时的存储位置不能一致时，绝不加载旧订阅。首次加载前发现变化时按已核对的身份恢复本次文件批次；候选已经加载、运行检查或回退阶段才发现变化时，恢复能确认的文件但不再加载旧路径，保留事务供下次在稳定状态下恢复。显式 `--profile-dir` 绑定调用方给出的规范目录，不套用本地/iCloud 存储判断，但仍核对当前订阅。

当前订阅或存储偏好必须能与读取失败区分；缺少 `selectConfigName` 可以表示默认 `config.yaml`，但偏好导出、解析或字段类型失败不能按空值继续。当前目录必须恰好匹配一个活动配置；零匹配或多匹配都停止，未完成的事务保持不变。

普通 Patch 的持久事务可能在当前订阅已加载候选、事务记录尚未删除时被强制中断。下一次 Patch 必须先恢复原文件，再重新加载当前原订阅；代理组选择只核对原订阅仍存在的选择器，候选临时新增的选择器不能阻止恢复。缓存、TUN、代理选择、国内与境外 DNS 和连通性全部通过后才能删除事务记录并开始新一轮校验；恢复失败时保留事务记录并停止。本次自动刷新失败、文件已恢复但原运行配置未恢复时，也必须保留同一事务供下次 Patch 重试。恢复入口使用 `--no-reload` 时不得删除事务或处理新候选，等待以后允许刷新时完成运行恢复。

备份恢复与普通 Patch 共用上述事务完成条件。开始备份校验前若存在未完成的配置事务，先恢复文件和当前运行配置；运行恢复失败时不删除事务，也不读取或写入备份。实际替换备份前另建持久事务；当前文件已与备份相同时，也用相同原字节和候选字节建立运行恢复记录。操作锁持续覆盖当前订阅的重新加载和运行检查；文件替换后被强制结束时，下次公开操作恢复替换前字节，运行回退失败时继续保留事务。

缓存清理后确认 TUN 仍启用、原有代理组选择没有变化、国内和境外 DNS 查询均成功、外网可连接。对用户报告的国内站点，还要比较 Mihomo 与两套大陆 DoH 的 A/CNAME、记录 HTTPS 分阶段耗时，并确认实时连接为 `DIRECT`；解析仍随代理节点位置落到境外 CDN 时继续修复。任何一步失败，都必须在当前进程内恢复写入前的原始字节，并在候选已被内核采用时再次加载原配置。控制器不可用时也恢复，不把修改后的当前订阅留给用户手动处理。不得调用 AppleScript，不得切换 TUN、订阅、代理组或节点，更不得退出、停止或重启客户端。

### Windows

Clash Verge Rev 每次加载或刷新订阅都会运行 `profiles/Script.js`。三个档位都安装全局扩展脚本并把数字档位写进受管代码：档位 1、2 只应用共同国内域名直连基线，档位 3 再应用完整策略。TUN 和顶层 IPv6 使用 Clash Verge Rev 的应用配置，因此不会被脚本后的应用设置覆盖。

自动查找 AppHome 时若 Roaming 与 Local 两个受支持候选同时存在，安装、卸载、备份、安全更新和诊断都必须拒绝歧义，不能静默选择其一。

Windows 不安装永久监听、计划任务或后台服务。三个档位都必须让 Clash Verge Rev 当前会话停止订阅自动更新；只写磁盘上的 `profiles.yaml` 会让内存继续刷新，并可能在客户端退出时被旧内存覆盖。因此客户端运行时不改用途档位、所有权、脚本或客户端配置，待客户端未运行时重试：档位 3 返回 `client_running_profile_three_deferred`，档位 1、2 返回 `client_running_auto_update_deferred`。三个档位的安全卸载同样不能在客户端运行时恢复 `profiles.yaml`、移除全局脚本或删除用途档位与所有权状态；只要本次卸载有受保护目标，就返回 `partial/client_running` 并整批不改，客户端停止后再重试。唯一例外是用户明确触发安全更新后，`-VerifySafeUpdate` 可以按本次不可伪造的清单把订阅文件恢复到刚创建且哈希匹配的备份；恢复前必须从已读取的备份字节验证清单哈希，坏备份不能先覆盖有效订阅。它仍不能声称运行内核已经恢复，后续必须单独做实时验收。自动更新修改器只处理 `type: remote` 项目；保留本地项目、订阅地址、更新时间、间隔和其他选项。三个档位写入时都把原来为 `true` 或缺少字段的 uid、原状态与原 `option` 形态写进独立所有权状态，并与 `profiles.yaml`、全局脚本和用途档位放在同一事务；档位 3 的应用设置也加入该事务。重复安装不能把已经写成 `false` 的状态误记为原值。无法唯一识别 `items`、`uid`、`type`、`option` 或目标字段，遇到大小写冲突 uid、锚点、别名、重复键、行内复杂映射、多文档与制表符缩进时直接拒绝。每次实际配置写入前备份，写入后重新读取并确认所有远程订阅都是 `false`；任一步失败时恢复整个事务。所有档位先确认可信路径中的 Mihomo 版本；只有档位 3 且客户端未运行时才继续用它检查应用配置候选并修改 TUN、IPv6 等应用设置。安装程序处理 `tun: null`、空格键名、行尾注释和块状 `dns-hijack`；无法安全合并的锚点与多文档 YAML 直接拒绝，`--- # 注释` 也算文档标记。同一应用目录的所有公开写操作共用目录内独占锁文件，并持有配置目录句柄；大小写、扩展路径、短路径、SUBST/映射或目录改名不能产生第二个锁身份。全部候选先生成并检查；事务要求每个规范化路径只有一个最终动作，拒绝写删重叠、重复目标、目录联接、符号链接、重解析点和硬链接；第一次修改前持有目标全部父目录与全部目标的句柄，阻止目录改名或联接点替换，并核对同一独占文件句柄读取的原字节、卷标识和文件 ID，内容相同但文件已经替换也必须拒绝。删除通过该文件句柄完成，不能在核对后再按路径删除。候选生成后的外部改动必须保留并拒绝覆盖。每个批量事务在首次修改前保存持久恢复记录；正常失败时通过仍持有的句柄恢复每一个目标，进程被强制结束时由下次公开操作先恢复原状态，不能在半完成事务上继续。恢复按原始字节保留编码和 BOM，遇到无法合并的新改动则停止。Windows 每次写入前创建带日期时间的版本化备份；备份先在同目录临时文件中完整写入、同步并改成私有权限，再原子发布正式 `.backup` 名称，进程中断留下的临时文件不会被列出、恢复或当作初始快照。备份目标键由相对应用目录的规范路径生成，不受目录改名或路径别名影响。正式备份只允许当前用户、SYSTEM 和 Administrators 完全访问。

中断的客户端敏感事务不能绕过客户端运行边界。事务记录和新建文件准备记录必须持久保存恢复权限；普通安装、卸载、备份恢复及旧版记录默认要求 Clash Verge Rev 停止，不能根据目标路径猜测事务用途。恢复时必须先独占锁定并核对全部恢复目标，再次检查客户端，确认仍未运行后才批量执行任何修改；客户端已运行或在恢复提交前启动时返回 `partial/transaction_recovery_pending`，保持目标字节和恢复记录不变。提交条件必须只返回一个布尔值。删除事务的目标缺失时，只能在同目录以私有 ACL 创建临时文件，完整写入原字节并执行 `Flush(true)`；提交条件通过且再次确认最终路径仍缺失后，才用不可覆盖的原子移动发布。条件拒绝或恢复中断时不能在最终路径留下空文件或原文前缀，也不能消费恢复记录。目标已换成不同文件身份时，只有完整原字节可以直接确认且不得改写；空内容、原文前缀或其他内容一律保留目标与事务并停止。以后任一公开命令再次进入同一目录时继续恢复。只有用户明确触发的安全更新可标记运行中恢复权限，且记录中的全部目标必须严格限定为 `profiles` 目录直属的 `.yaml`/`.yml` 远程订阅和本次 `claude-easy-safe-update.json` 验收清单；目标越界或权限未知时按需停止客户端处理。

安全更新验收失败且整批允许恢复时，订阅恢复与本次验收清单删除必须属于同一个可恢复的写删事务。冲突、坏备份或事务失败时保留清单并保持整批零改动；进程中断后不得用已经恢复的旧订阅重新验收并报告本次更新成功。

通过已锁定原文件句柄写入替换字节和失败恢复原字节时，都必须先把文件截为零长度，再写入目标内容并同步。这样，中断状态只能是空文件或当前目标字节的前缀，事务恢复可以可靠识别并恢复；不得先覆盖较短内容再依赖事后截断，因为进程可能在截断前留下旧尾部。

批量事务包含原本不存在的写入目标时，必须先确认全部新路径仍不存在，再以原子发布的私有准备记录登记规范相对路径；在此之前不得创建任何最终目标。取得新文件句柄并发布包含文件身份的主事务记录后，先删除准备记录，再开始写入。若进程提前中断，下次公开操作在读取用途档位或其他内部状态前处理准备记录：只删除仍为零字节、非链接、无硬链接且身份在检查期间未变化的目标；缺失目标直接略过，非空内容或身份变化按外部修改拒绝。准备记录损坏时停止，不能猜测删除。

Windows 全局脚本也必须做二次转换一致性检查；结果不一致时返回原配置。任何流程都不得结束、暂停或重启 Clash 进程，也不得要求用户这样做。

组合 `Script.js` 时，只把代码状态中的独立行注释当作补丁边界；普通字符串、模板字符串的文本部分和块注释中的相同文字不是边界，模板表达式仍按代码检查，嵌套花括号不得逃过校验。已有脚本只允许一个同步 `function main` 声明；当前解析能力不能可靠重命名正文引用，因此唯一入口声明之外任何裸 `main` 引用都必须拒绝，包括 `main.version`、`const handler = main`、对象简写、再次作词法声明或裸赋值。使用补丁保留标识符、异步 `main`，或会在重命名后误调用补丁入口的递归 `main` 时，安装器也必须拒绝并保持整批文件不变。`eval`、`Function`、函数的 `.constructor` 和值恰为 `constructor` 的单、双引号字符串会脱离可验证边界，也必须在写入前拒绝。组合器先运行私有 setup，捕获受管引擎、真实全局，以及 `Object`、`Reflect`、`Array`、`Boolean`、`Error`、`Function`、`JSON`、`RegExp`、`String` 和相关原型的完整描述符。改名后的旧脚本直接放在专用原脚本边界内，仍位于 Clash 自己的真实 `try`/Script 顶层，不增加函数或回调层；它的顶层 `var`、函数、`globalThis`、`this` 与开头 `"use strict"` 字符串必须保持客户端直接加载时的行为。旧顶层结束后，finalizer 先恢复并核对内置对象，再把执行器可见的全局 `main` 定义为不可配置的受管访问器；旧顶层对 `globalThis.main` 的改写因此会被最终入口取代。受管入口调用改名后的旧 `main` 时使用 Script 的调用方式，并在 `finally` 中恢复、核对内置对象；旧函数正常返回后才运行 ClaudeEasy 变换，抛错时也必须先完成恢复。受管函数始终留在私有作用域，普通全局写入仍发生在真实执行环境。安全更新比较受管区块时忽略专用原脚本边界内的用户代码正文，但必须逐字核对边界外的引擎和组合结构，并要求整个受管区块外只有空白或注释；任何可执行前缀、后缀或额外 `main` 都拒绝验收。重装必须在组合检查通过后把区块外旧代码迁入专用原脚本边界并保留，卸载再从该边界恢复。

首次安装把 `config.yaml` 与 `verge.yaml` 的原始字节和安装后哈希写进本地状态文件。安装状态、用途档位状态、自动更新所有权状态和安全更新清单都必须是非链接普通文件，使用严格 UTF-8、唯一字段和精确版本/类型结构；每个流程只读取一次，同一份字节同时用于解析、决策、冲突检查和删除。内部状态不得作为普通单文件备份恢复。卸载先生成 `Script.js`、订阅自动更新与应用设置的全部候选，再检查全部写入和删除目标；任一冲突时整批零改动。删除文件时必须在持有阻止同文件读取、写入、改名和替换的句柄期间核对字节并删除；失败恢复也不得覆盖恢复期间出现的新内容。卸载时只有当前哈希仍与安装程序最后写入的版本一致才恢复；检测到安装后新改动时保留当前文件和全部状态，不能覆盖。三个档位的安全卸载只要需要修改任何受保护文件或状态，客户端运行时就整批返回 `partial/client_running` 并保持用途档位、所有权和全部目标不变；事务锁定并核对目标后还要再次检查，防止客户端在提交前启动。不得要求用户退出、停止或重启客户端。Windows 的订阅增强只在各订阅随后加载或刷新时发生，安装完成不能说所有订阅已经处理。

## 异常处理

- `401 unauthorized`、HTML、空文件或损坏 YAML：写成“已跳过：订阅内容无效”，等待以后刷新出有效订阅。
- Mihomo 拒绝候选文件：保留原文件，写成“已跳过：内核校验失败”。
- Mihomo 版本检查或候选校验超过 30 秒：终止本工具启动的 Mihomo 校验子进程，保留原文件，写成“已跳过：订阅响应超时”，继续处理下一份订阅。
- YAML 候选的二次转换与第一次不同：保留原文件，写成“已跳过：二次转换不一致”。
- 找不到 Mihomo、版本低于 1.19.27 或无法读取版本：停止安装，不写入任何目标文件。
- 读取或写入失败：保留能保留的原文件，写成“已跳过：读取或写入失败”，不能伪装成订阅无效。
- 找不到主代理组：不修改，不猜节点。
- 没有已有 AI 分组，并且订阅中找不到任何有效内联节点或代理提供者：不创建空组，写成“未修改：找不到可用的 AI 节点”。
- 已有 Windows 全局脚本只有一个同步 `main`：先运行原脚本，再运行 ClaudeEasy 补丁。Clash Verge Rev 当前不会等待 Promise，因此必须拒绝 `async function main`。
- 已有 Windows 脚本结构无法安全组合：保留原文件，请用户发送提示和 `Script.js` 截图。
- 两端都原样保留已有的 REALITY `short-id` 文本，不补齐、不截断、不猜缺失值。macOS 读写 YAML 时显式保护容易被误判为数字的有效十六进制文本；Windows 的对象转换不得改变该字段。
- 当前配置只有自动刷新和运行检查全部通过，才能写成“已更新并自动生效”。刷新失败并恢复时写成“自动刷新失败，已恢复原配置”；文件恢复但内核未恢复时必须单独说明。
- ClashX Meta 正在运行时保持运行，不调用 AppleScript，不修改 `restoreTunProxy`，不切换 TUN 或代理节点。
- 远程 `proxy-providers` 在 Mihomo 写入前检查中可能需要网络；离线检查失败时保留原文件，并提示联网后重试。

## Patch 验证标准

档位 1 只验收系统代理与 Google、Twitter、用户常用站点；档位 2 只验收 TUN、Clash 自己的系统代理开关、Google、Twitter、ChatGPT、Gemini 和一个命令行或 Agent 连接。不能因为未运行泄漏测试而把档位 1、2判为失败。以下完整验收只属于档位 3。

先生成 Google、OpenAI 和 Claude/Anthropic 的真实连接，同时读取 Mihomo `/connections`、`/rules`、`/proxies` 与 `/providers/proxies`。macOS 运行 `ruby scripts/macos/verify_routes.rb`，可用 `--main-group`、`--ai-group`、`--observation-seconds` 调整；Windows 运行 `powershell.exe -NoProfile -File scripts/windows/verify_routes.ps1`，对应参数为 `-MainGroup`、`-AiGroup`、`-ObservationSeconds`。Windows `-ControllerUrl` 只允许本机回环 HTTP/HTTPS，不接受 userinfo、查询或片段；控制器密钥只经标准输入交给 `-SecretStdin`，非空 `-Secret` 必须拒绝，请求禁用系统代理和重定向，命令行、环境变量、输出与日志都不能出现密钥。两端都从 `/rules` 的最后一个 `MATCH` 读取当前运行配置实际使用的主代理组，并从 `/proxies` 的当前内存状态识别 AI 分组，不再从磁盘配置或固定名称单独推断。每个测试请求必须先绑定独立源端口，观察器只接受启动后出现且 TCP、源端口和目标域名全部匹配的连接 ID；同域名的浏览器、更新器或后台连接不得代替测试请求。验收结合 `chains` 与 `providerChains` 查出本次连接的实际叶子类型，整条链出现 `Direct`、`Dns`、`Reject`、`RejectDrop`、`Pass`、`PassRule`、`Compatible` 或 `Rematch` 均失败，即使出站使用自定义名称也一样。Google 的连接链必须包含当前主代理组；若订阅有明确的 Google 专用组，也可包含该非 AI 组，但不能经过 AI 分组。AI 网站的连接链必须包含 AI 分组。`Selector`、`URLTest`、`Fallback`、`LoadBalance` 和 `Relay` 都以实际连接链为准；没有 `now` 的主代理组或 AI `LoadBalance` 都使用观察到的叶子，请求前的 `now` 只用于预检或显示。JSON 成功码为 `routes_verified`，失败码为 `route_verification_failed`；每项检查状态只取 `passed`、`failed` 或 `not_observed`。只看配置文件或网页出口 IP 不足以证明分流正确。

然后必须测试：

1. `https://ipinfo.cv/webrtc-check`
2. `https://ip.net.coffee/dns/` 的“深度测试”
3. `https://ip.net.coffee/webrtc/`

三项都没有红色提示，并且不显示用户未代理的公网 IP、私网地址或本地运营商 DNS，才算通过。

三项均为第三方页面，会接收浏览器的公网 IP，并发起 WebRTC 或 DNS 测试请求。补丁不向这些页面上传订阅、节点密码或配置文件；用户可以拒绝使用，结果写成“未验证”。

macOS 和 Windows 只要当前代理工具提供 Computer Use，就由代理打开页面、点击“深度测试”并读取结果，不把刷新或测试停给用户。当前环境没有 Computer Use 时，要求用户手动测试。只要有红色结果，就让用户发截图并继续处理，不得说已经验证。

## 输出格式

档位 1、2 先报告保存的用途、客户端开关、未应用的补丁和对应站点复测。档位 3 再逐一输出订阅：

```text
订阅名称：已更新并自动生效
AI 组：复用原有 AI（成员未改），或新建独立 AI 选择器（包含全部可用节点和代理提供者）
安全代理组：未创建；直连 DNS 使用大陆 DoH，普通代理 DNS 使用原主代理组，AI DNS 和 UDP 使用 AI 分组
主代理组：节点选择
节点建议：请自行选择家宽；有台湾时优先台湾，没有时可选日本
配置中的 TUN：已写入；运行状态：已自动刷新并验证
持久化：未安装
DNS 测试：通过
WebRTC 测试 1：通过
WebRTC 测试 2：通过
```

未完成浏览器测试时把测试状态写成“未验证”。

订阅状态只能是：无需修改、已更新并自动生效、已更新，尚未自动刷新、已更新，选择该订阅时生效、自动刷新失败，已恢复原配置、自动刷新失败；文件已恢复，运行内核恢复失败、自动刷新失败；订阅同时发生变化，未覆盖新内容、未修改：找不到可用的主代理组、未修改：找不到可用的 AI 节点、已跳过：订阅内容无效、已跳过：内核校验失败、已跳过：订阅响应超时、已跳过：二次转换不一致、已跳过：策略版本无效、已跳过：订阅正在刷新，稍后重试、已跳过：读取或写入失败、已跳过：处理失败、未修改：客户端不受支持、未验证：需要手动测试。当前订阅只有自动刷新和运行检查通过后写成“已更新并自动生效”；未选中的订阅修改后写成“已更新，选择该订阅时生效”。
