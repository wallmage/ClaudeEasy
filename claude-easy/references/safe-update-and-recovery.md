# ClaudeEasy 订阅更新与恢复策略

> 读取路由：用户明确要求更新订阅、列出或比较备份、恢复配置，或维护备份恢复行为时读取本文件。所有网络任务先读取 [policy-core.md](policy-core.md)；本文件不重复共同边界。

## 更新全部订阅

### 完整任务顺序与完成条件

平台命令返回 `safe_update_completed` 或 `safe_update_verified`，只表示订阅、补丁和平台检查已经完成，不代表用户要求的订阅更新任务已经完成。机器结果出现 `workflow_complete: false` 时，必须继续完成 `required_followups`，不得把中间回执当成最终说明。

完整顺序如下：

1. 只读取已保存档位和更新所需状态；更新前不运行任何测试，不做站点、Agent、分流、DNS 或 WebRTC 基线。
2. 为全部远程订阅创建备份。macOS 随后自动下载；Windows 通过 Clash Verge Rev 的“更新所有订阅”执行客户端原生刷新。两端都按已保存用途档位重新应用现行补丁并完成平台检查。
3. 更新成功后，完成与首次运行该档位相同的平台客户端动作和验收。安全更新已经重新应用订阅文件补丁，不得再次运行平台安装命令。档位 1 执行档位 1 全部动作和验收；档位 2 继承档位 1 的共同补丁与站点验收，但档位 2 不执行档位 1 的系统代理开启动作，而是直接执行档位 2 的客户端开关；档位 3 继承档位 2，再完成 ChatGPT、Gemini、Grok 分流验证、DNS 深度测试、WebRTC 测试和本地区域指纹测试。Claude/Anthropic 不打开、不请求、不测试任何远程域名。
4. 做最终状态复核：逐份确认本轮订阅更新状态、已保存档位、补丁、运行配置、代理组选择、客户端开关、订阅自动更新关闭状态和未完成事务。

Windows 订阅刷新和 Windows 客户端开关在当前会话提供电脑操控时由代理操作；没有或首次调用失败时先按主入口帮助启用，再按 Windows 平台规则处理。macOS 更新后的 `macos_client_switch_reconciliation` 运行原生开关协调命令，绝不使用电脑操控操作 ClashX Meta。两端的浏览器验收有电脑操控时都由代理完成；确实无法启用时才把最少界面动作交给用户并读取结果。未验证项目不得宣称完整完成。

只有全部远程订阅和当前档位规定的全部验收都有本轮结果，且强制完成闸门通过，才可输出完成说明。失败或未验证项目先继续诊断、修复和复测；只有真实阻塞才按主入口给用户一个必要动作。

### 180 秒更新窗口与最终成功闸门

macOS 从启动安全更新命令、Windows 从开始客户端“更新所有订阅”起，为同一轮更新设置 180 秒总等待上限。计时只限制更新尝试，不限制随后查明和修复问题所需的诊断时间。180 秒内没有取得最终成功结果时立即停止等待，不得原样重试：macOS 只中断本轮由代理启动且仍在运行的前台命令，不停止或重启 Clash；Windows 停止继续验收，不重复点击更新，再执行一次现有安全恢复，恢复时间不计入 180 秒。恢复成功在内部记录超时和回滚；恢复未完成返回 `partial` 并保留恢复记录。随后立即读取最终命令结果、事务记录、运行状态和日志，确认失败阶段，继续诊断和修复；修复完成后才允许进行一次新的真实更新验收。

下载完成、候选写入、客户端收到加载事件、日志显示新配置完成加载，或前台命令仍在运行，都只是中间状态，不能报告成功。只有平台命令已经结束且退出码为 0、机器结果没有 `failed`、`partial`、`rolled_back` 或 `safe_update_rolled_back`、全部 `required_followups` 已通过，并且最终复核确认没有未完成事务、没有回滚、原 TUN 与代理选择已恢复、订阅自动更新仍关闭，才可向用户报告更新完成。任何候选后来恢复成旧配置都在内部记录为失败并立即继续诊断；只有最终仍被真实阻塞或用户主动询问时，才用日常语言说明原设置已恢复和下一步，不能把短暂加载成功改写成整轮更新成功。

用户说“更新节点”“更新订阅”或同义表达时，按用户意图更新当前存储位置中的全部远程订阅，不切换订阅、代理组或节点。

首次收到请求时，先提醒：“请确保订阅开关已打开。请自行登录服务商管理后台，找到订阅开关并打开；部分服务默认关闭，开启后约 10 分钟有效，到期会自动关闭。打开后回复‘打开了’或‘没问题’，我再继续更新。”用户同一条消息已经明确确认开关打开时直接继续；否则确认前不得读取订阅、建立备份或操作客户端。不得代替用户操作服务商后台。

确认后执行：

1. macOS 运行 `bash scripts/install_macos.sh --safe-update --json`；Windows 先运行 `.\scripts\install_windows.cmd -SnapshotProfiles -Json`。两端都先为全部远程订阅创建更新前备份，任一备份失败时停止；Windows 同时只读记录更新前 TUN 与全部代理组选择。备份和更新前不得运行验收测试。
2. macOS 通过 Foundation 原生网络请求自动下载全部远程订阅，请求身份从当前运行的 ClashX Meta 应用信息动态生成，并发送 `Accept-Language: zh-CN,zh;q=0.9`。Windows 不直接下载订阅：先检查当前工具列表是否提供电脑操控（Computer Use）；提供时用它操作已经运行的 Clash Verge Rev，进入“订阅”并确认自动更新关闭，紧接着运行 `.\scripts\install_windows.cmd -BeginSafeUpdateRefresh -Json` 后点击顶部“更新所有订阅”并等待刷新完成。180 秒从清单中持久保存的刷新开始时间算，不从备份开始。不得使用右键菜单中的“更新”或“通过代理更新”，以免 Clash Verge Rev 2.5.2 把自动更新重新打开。
3. Windows 当前会话没有电脑操控，或首次调用失败时，不原样重试；先按主入口识别工作台并帮助启用。确实无法启用时，才让用户打开“订阅”页并回复“准备好了”；收到回复后立即运行 `.\scripts\install_windows.cmd -BeginSafeUpdateRefresh -Json`，再让用户只点击顶部“更新所有订阅”，完成后回复“更新好了”。收到后运行 `.\scripts\install_windows.cmd -VerifySafeUpdate -RefreshConfirmed -Json`。电脑操控自动刷新成功时也运行同一命令。清单里的 `RefreshStartedAt` 是刷新开始凭据，`-RefreshConfirmed` 是刷新完成凭据；订阅字节和时间戳未变化也可以是有效结果。
4. macOS 在写入前完成严格 UTF-8、YAML、代理组、二次转换一致性检查和 Mihomo 校验，全部候选通过后才整批写入。Windows 刷新时由 Clash Verge Rev 运行已安装的全局脚本，按已保存用途档位重新应用补丁；验收命令逐份确认本轮刷新，核对全局脚本与已保存档位，并完成严格 UTF-8、YAML、代理组和 Mihomo 校验，同时恢复并核对更新前的代理选择和 TUN。Windows 在候选加载与失败恢复前分别从锁定的同一运行文件版本持久记录内容指纹和当前客户端身份；每个持久阶段最多发送一次重新激活快捷键，中断或客户端更换后都只读验证，不再次发送。失败时恢复更新前备份并重新加载原运行配置；成功后再次确认订阅自动更新关闭。
5. 两端都不得切换订阅、代理组或节点；两端都保留更新前的 TUN 与代理组选择。最终状态复核必须确认这些状态没有被本轮更新改变。平台更新成功后按 `required_followups` 完成已保存档位客户端动作和全部验收；macOS 运行 `ruby scripts/macos/patch_profiles.rb --reconcile-client-switches --usage-profile N --json`，Windows 按界面规则处理。电脑操控不可用时按 `SKILL.md` 先帮助启用，确实不能使用才请用户完成必要点击；不能因此减少补丁、测试或最终复核。

macOS 安全更新当前订阅时，由同一已运行 ClashX Meta 进程的官方更新事件重新加载，本地控制器只用于观察和验收；不得直接重载 Mihomo 或修改 TUN。

macOS 不得用 curl 下载订阅，也不得固定或伪造 User-Agent；只能从当前运行的 ClashX Meta 版本、构建号、标识和系统版本动态生成与客户端一致的原生请求身份。Windows 不直接构造订阅请求，只使用 Clash Verge Rev 的客户端原生刷新。两端不追加通用的防倒退、数量、哈希或时间戳检查；但当前配置含 AnyTLS，而新配置完全失去 AnyTLS 并改为 Shadowsocks 时，必须拒绝接受本轮更新。平台命令内部不追加 WebRTC 检查；命令返回后仍按已保存档位完成任务验收。

配置历史用于诊断与回滚：macOS 下列备份参数都由 `ruby scripts/macos/patch_profiles.rb` 执行，不能传给 `install_macos.sh`。当用户说某次改动后变慢或断网，先用 `--list-backups` 列出备份，按 `created_at` 选择症状出现前最近的一份作为候选，再用 `--compare-backup ID` 把当前配置与候选做配置差异比较；两端公开的备份 ID 统一为不含真实文件名的 `ce-backup-v1-<64 位十六进制>`，旧原始编号只作为兼容输入，不能再次输出。JSON 列表在 `items` 返回含 `id` 与 RFC 3339 `created_at` 的对象；JSON 比较在 `items` 返回 ID、是否相同、备份 SHA-256 与恢复所需的当前 SHA-256，使列出、比较、恢复可以直接衔接。时间接近只能帮助选备份，不能仅凭时间接近就判定某项变化造成故障。不得自动删除历史备份。macOS 恢复使用 `--restore-backup ID --expected-current-sha256 SHA256`；Windows 使用 `-ListBackups`、`-CompareBackup ID`、`-RestoreBackup ID -ExpectedCurrentSha256 SHA256`。恢复前验证备份 YAML 与 Mihomo、核对目标文件和预期 SHA-256，并为当前版本再建备份；恢复后复测原始症状，恢复或运行检查失败时恢复回滚前版本。macOS 备份恢复、Patch 与订阅更新前备份共用操作锁，并在读取备份和写配置前先恢复未完成的批量事务；事务恢复改变当前字节时，本次请求按预期哈希冲突停止，必须重新比较。备份事务把提交后的真实路径和文件身份交给运行加载与失败回退；外部以相同字节替换目标也不得覆盖。macOS 恢复当前订阅后通过 Mihomo 本地控制器重新加载；保持恢复前的 TUN 开关与目标仍保留的代理组选择，并完成缓存、DNS 和连接检查，失败时恢复回滚前版本。文件恢复但运行内核未恢复，以及 Windows 客户端运行导致暂时不能安全恢复，都只在内部记录并继续寻找安全路径；确实需要用户动作时按 `SKILL.md` 只说明一个步骤。恢复非当前订阅时不得切换当前订阅。
